# Slime 源码阅读约定

本目录围绕 Research Agent 框架工程组织阅读：先定位各模块职责，再追踪模型、工具、任务、上下文、Trace、结果、评测与训练的交接。复用仓库根目录的[通用工作流](../../00-repo-reading/workflow.md)，认知步骤在 [Slime 项目入口](../../00-repo-reading/repositories/slime/README.md)；当前进度和下一步以 [repo-reading-route.md](repo-reading-route.md) 为唯一记录。

## 每次接续：先定位目标与进度

- 无论聊天讲解、规划还是页面修改，回答前先读通用工作流、Slime 最近一步、本文件、[路线的当前接续](repo-reading-route.md#当前接续)和 [岗位对照的当前安排](job-alignment.md#当前学习条件与投入安排)。这些文件承接已确认的目标，不要求用户每轮重新说明 JD、硬件条件或已读范围。
- 最新用户反馈优先于旧的“当前优先”“未开始”或目录位置。发现冲突时同轮更新接续及过时入口，不能把源码版本变化、材料 planned/ready 状态或缺少复述验收解释成用户没有读过。
- `repo-reading-route.md` 唯一维护当前已读范围、理解状态、运行状态和下一步。步骤文件保留当时的理解与证据快照；章节 README、review、派生清单引用当前接续，不维护第二份实时状态。“已读”不自动升级为“已掌握”或“已运行”。用户明确报告已读、仍不懂、跳过或改读上游时，及时记录，不等待额外的“请记住”。
- 已读也不等于随时能回忆。首次重遇已读组件时先短提醒“负责什么、接到什么、交回什么、在当前链条哪里”；按具体追问补缺口。用户说需要提醒时保留已读事实，不自行断言忘了哪些机制。形成新的个人记忆或用户要求模拟时，按 repo-reading-memory 邀请复述并根据回答追加细节问题；已有明确表述或纯粹继承旧记忆时无需重复，不把复述作为继续阅读或承认已读的前置条件。
- JD 决定详略与投入；时间比例只在 `job-alignment.md` 维护，作为可调整的初始预算，不冒充实际耗时或岗位能力覆盖率。独立 Python 异步专题仍沿用其自身课程与进度。

## 全局与局部一起带读

- 每次进入一个新组件，先用简短文字或一条调用链交代：当前框架问题、调用者 → 当前组件 → 下一交接，以及为什么值得在此投入。聊天可说明岗位对应责任，公开正文只写技术目标。
- 再沿真实调用解释输入、主要行为、输出或副作用、运行位置和关键清理。已读组件先简短唤起，再在当前交接中使用；根据具体卡点补细节，不把“读过”当成无需提醒的已知前提。
- 讲完回到调用者，更新这段代码对全局数据流或控制流的作用，指出下一处尚未展开的交接。全景图沿同一条主线增补；简单关系用文字即可，不要求每轮重画全图或增加新目录。
- 一轮围绕一个明确问题，展开走通交接所需的关系，先正常路径，再补与当前岗位能力有关的失败分支。全局速览以能定位调用与职责为停止点，随后深入策略/评测、Trace/验证、并发/恢复；训练和资源先理解交接，再按需求深入。
- 引用单元时写完整名称并给入口；00–07 是本地阅读分组，01–26 是源码索引，4.1 是既有材料章节，临时列表号只是当前列表。不能混用这些编号暗示同一套执行步骤。
- 官方文档用于核对概念和接口，本地 00 用于职责定位，本地固定版本源码用于实际调用证据。每轮确定一个接续入口，不因页面名含 Get Started 就重开一条入门路线。

## 心智模型的递进与持续正文

- 全景从目标和最小端到端职责开始，不以已读过 `generate()` 为前提。已读历史只决定重遇时提醒多少；先建立基本框架，再逐步展开模块，不能把全景写成围绕已读函数补外围知识。
- 实际展开新问题时，在根目录 `00-repo-reading/repositories/slime/steps/` 创建下一步文件夹，使用 `01-scope.md`、`02-short-term-memory/`、`03-long-term-memory/` 和 `04-flow.md`。下一步 `03` 合并上一份 `03` 与 `02`，新认识写入新的 `02`。追问补在同一步，纠正保留前因后果；不为已有讨论虚构完成步骤。
- 两层记忆使用 [repo-reading-memory skill](../../.agents/skills/repo-reading-memory/SKILL.md)，[格式参考](../../00-repo-reading/memory-format.md)包含整体地图和镜像源码路径的逐函数记录；当前按用户认可的样例先保留原话，再列简短场景、调用代码、一组输入输出与 LLM 模型，最后列未知和来源。技术结论以源码为依据，修正文档不等于用户已确认理解，采用 skill 中独立的短期、长期 reference 模板。保留首次接触和最近认识更新，源码解释不算用户新增理解。当前 [Step 01 推演](../../backlog/repo-reading/step-01-translate-preview/README.md) 保留实际学习记录，新模板采用紧凑版式；旧步骤保留历史快照。
- 沿用用户认可的 Learn Claude 方式：已有骨架 → 当前新增需求 → 展开或调整的真实机制 → 接回原骨架。Slime 的全局保留职责、输入输出和运行边界，深入范围按岗位对照取舍；不把完整地图等同于完整通读所有实现。
- 教学骨架从固定版本真实源码裁剪，保留接口、函数名和数据合同，说明省略范围。“逐步展开”表示阅读层次；没有 Git 证据时不写成 Slime 的历史发展，也不另造一套通用框架。
- 用户已授权持续将带读过程和关键澄清整理到相应 walkthrough，并在 Hugo 阅读。保存问题怎样引出、已有理解怎样接续、代码提供什么证据、解释怎样补齐或修正关系、最后怎样回到全局；不只追加最终结论或聊天摘录。
- 用户明确表达过的理解与助手提供的解释分开。未明确反馈时标为可修订的解释模型，不用第一人称替用户写“我已理解”；沉默、“继续”、构建成功和材料生成都不是掌握证据。
- 个人认知记录先听用户怎样说函数的作用与目的；助手定位、提问并核对实际调用，为记录提供独立标注的场景、输入输出和 LLM 模型。只知道接口、不清楚机制时保留该状态，实现细节允许留白。完整讲解放参考，LLM 模型不自动变成用户理解；本规则不要求将完整教学正文改成留白。
- 新问题或纠正同轮补进对应段落，保留仍有解释价值的来龙去脉，合并无意义重复。已授权的持续增补不逐次请求确认；大幅重排已采用正文时仍先给差异对照。
- Walkthrough 保存连贯的技术解释，review 保存理解检查与验证建议，路线保存唯一进度。Hugo 从同一份 authored Markdown 渲染；公开正文不写招聘原文、时间预算、个人履历或私有进度表。

## 源码与材料维护

- 每次开发阅读材料或网站页面，先按仓库根 `AGENTS.md` 启动或确认本地 Hugo 预览，验证相关页面并给出本地链接，供用户边看边理解。
- Slime 源码仓库已确认后持续沿用，开始新章节也不重复询问。用户明确更换路径、尚未确定仓库或候选有歧义时才确认；读取源码前仍核对 Git 根目录、HEAD 和工作区差异。
- 开始新的阅读单元或调整重点时，对照 [job-alignment.md](job-alignment.md) 的相关需求行。讲解和回顾需关联模块责任、扩展接缝、失败情景与验证证据；一般文案修改无需重新浏览全部需求。
- 持续沿用已确认的 Slime 仓库；2026-10-19 本机实际根目录为 `/home/hongshi/projects/slime`，历史 `/home/fredkeira/projects/slime` 路径不可用。当前提交与旧材料版本分开记录在路线中，不因此重复询问仓库。`slime/` 是核心包，`examples/`、`train.py`、`tests/` 也在阅读范围内。
- 4.1 Action 的正文、图与源码入口同步存档到其对应章节文件夹；全局 00 的正文和资源保存在 `chapters/00-overview/`，不塞进单任务章节。code-reading 保存唯一路线和 authored 讲解；Hugo 与必要存档从同一维护来源同步。Pre-4 已有独立存档文件夹。
- 本目录保存阅读材料；保留原有 `slime_photo` 图文和源码仓库已有阅读记录。进入源码仓库的新会话时，明确读取本文件和路线；这个文件不会跨仓库自动生效。
- 开始或续读时，按 README 的版本核对步骤检查源码 HEAD、工作区差异、官方 THUDM/slime main 和路线中的固定版本；记录是否一致与差异，不能用 fork 的 origin/main 代替官方查询。源码更新后先说明影响，再有意识地更新入口；旧图和旧行号不当作当前源码证据。
- 第一遍覆盖模块职责。每个单元先回答：做什么、在哪里运行、输入输出、调用者和被调用者、可替换接口、失败后谁清理。第二遍按问题追踪关键分支。
- 页面正文与源码校验分层：文件路径、行号和固定源码链接放在对应解释附近的折叠入口，另有独立 `SOURCE-CHECK.md` 集中核对；用于理解的局部图和示例不因隐藏出处而一并收起。Action 2、Action 3、3.5、Action 4 和 Action 5 已采用这一形式，其他章节经确认后逐步迁移。
- 章节格式审阅、改写或制作对比稿时，使用 [code-reading-chapter](../../skills/code-reading-chapter/SKILL.md) 及其模板。它统一局部图、真实调用、数据交接、按需源码与复述层次，不固定步骤数；只接入现有图文的请求不等于授权改写正文。已存在的正文改稿先提供对比，用户确认后采用。
- 4.1 Agent Rollout Adapters and Harnesses 保存单份任务的完整导览，可用于回查准备、启动、模型请求、收集、评分、导出与清理。是否继续读其内部，以路线的最新接续为准；在整体主线进入该组件时短回顾已读部分，再返回调用方。
- Pre-4 独立说明进入 Harness.run 前的调用方准备，目录位置在现有 3.5 后、4 前。现有 3.5 保持模型请求收尾的职责；目录位置不当作执行时间，整体按任务阶段分组阅读。
- 每个 Action 保留独立阅读语境与主要源码入口：局部图后、具体代码前说明当前主线、本章职责和返回位置；文件、符号与行号默认折叠。共用映射为 `action-contexts.json`，解释见 `action-contexts.md`；Hugo 从映射渲染，不另维护一套章节文件清单。
- 当前章节统一以“阅读问题 → 短导航伪代码 → 本节图 → 真实代码讲解”展开。导航只带过前后调用并标明本章入口，记录在 `action-navigations.json`；不是源码摘录，不提前复制详细实现。HTTP 请求章标明运行期间的交互，环境能力章标明调用后返回，不把 Action 编号当成执行顺序。
- 每一个 Action 文件中的阅读伪代码都标明省略部分属于哪些 Action、职责覆盖到哪里，不能只保留裸省略号或“前面已读”。Action 5 标明环境能力的跨阶段复用；7→2→3→3.5 标明发生在 CLI 运行期间，不当作 Action 6 返回后的流程。
- `generate()` 编排一次样本任务；多轮模型/工具循环由运行中的 CLI 推进。2 → 3 → 3.5 展开 `BaseAdapter._run_turn()` 内的一次请求；Pre-4 与 4 跟随任务准备和 Harness 启动；5 是环境能力，6 是调用这些能力的长命令执行机制，7 是 CLI 回连 Adapter 的入口。同一个源码文件可承载不同职责，不能把这些实现都归入 `generate()`，也不能将动作编号当作顺序执行的阶段。
- 既有 4.1 导览采用 Claude Code / Anthropic；Codex / OpenAI 保留为实现对照，协议名不能当成实际模型供应商。该选择不要求重新阅读已读任务链。
- 26 项整仓清单用于定位和扩展，不覆盖路线中的当前接续。后续详略按岗位对照和用户反馈调整，不把清单顺序当成每项都需同等投入。
- 用户说“快速看一下”时给职责地图、少量骨架源码和复述问题；用户指定深入某单元后再展开实现。默认一轮一个单元，沿用已确认的顺序和深度。
- 说明每段源码的实际行为、扩展接缝和外部边界。区分 Slime、CLI 工具循环、模型服务、沙箱、Ray 与 Kubernetes，不能把协议名当作实际模型供应商。
- 用明确的能力目标组织内容，不把招聘原文、岗位要求或求职叙述展示在网站上。
- 阅读阶段采用当前固定版本的静态调用与数据关系。需要讨论历史成长时另查 Git 证据；同一版本的阅读层次不能写成历史阶段。
- 源码链接绑定文件、符号和固定提交。`source-map.json` 是入口核对清单，不是运行记录，也不证明整文件已掌握。
- 路线或入口更新后同步章节目录、`code-reading-list.md` 与网站“源码阅读顺序”页。最终名单是路线中“最终代码阅读清单”的派生视图，优先修改唯一阅读路线再同步；不要另维护一套顺序或学习状态。用 repo-reading-workflow 的 scaffold 检查目录，用源码存在性与符号检查核对链接；内容或导航改变时检查 Hugo 构建。
- `walkthrough.md` 记录讲解，`review.md` 记录复述问题与验证证据；当前学习状态只在路线维护。未运行任务标为建议，用户明确的阅读反馈可以更新已读范围，掌握与实际运行另记，不把三者合并。
- Kubernetes 集群经验和外部 CLI 内部工具实现需要独立实践。阅读、生成材料、静态核对与实际运行分别记录。

文件分工：`AGENTS.md` 保存约定，`job-alignment.md` 保存需求与阅读单元的对照，`repo-reading-route.md` 保存顺序、深度、版本与状态，`chapters/` 保存各单元入口和后续讲解，`COVERAGE.md` 汇总范围与缺口。
