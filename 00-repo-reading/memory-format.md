# 短期与长期记忆：要求、格式与讨论记录

[方法入口](README.md) · [工作流](workflow.md) · [函数模板](templates/function.md) · [单步模板](templates/step/README.md)

这份 Markdown 专门保存 short-term memory 与 long-term memory 的要求、当前格式，以及我们为什么这样设计的讨论。以后关于这两层记忆的新要求、修正和待讨论问题，继续在这里维护，便于接续。

可执行的 skill 入口是 [repo-reading-memory](../.agents/skills/repo-reading-memory/SKILL.md)：它负责指导助手执行。本文件保存要求和讨论依据；当讨论形成新的执行规则时，同步修改 skill。具体函数的学习问答仍保存在对应步骤的 `04-flow.md`，并由该步骤的 memory 引用。

当前格式采用紧凑函数记录：原话、简短场景与源码、一组 Input → Output、LLM 补充模型、未知、来源。原话已经清楚时不再另写重复的“当前心智模型”；短期和长期各有独立 reference 模板，正文一致，长期只补继承来源。

本文件规定 `02-short-term-memory/` 和 `03-long-term-memory/` 中每份 Markdown 显示什么。两层记忆使用同一套字段，区别是收录范围与更新时机。依据是用户已经确认的“哪一步遇到、作用的心智模型、尚不清楚的边界”，以及两个函数记录的实际试用。

## 用户明确提出的要求

1. **保留用户对函数最直接的表述。** 在函数记忆正文开头逐字引用；原话已清楚时无需重复归纳，保留在哪一步遇到它。
2. **让用户用自己的话复述。** 助手负责定位和引导，个人心智模型来自用户的实际解释。
3. **根据复述追加细节问题。** 助手主动发现值得澄清的关系，逐次提问，而不是只抄录第一句答案。
4. **实现可以留白。** 知道作用但不清楚如何实现，应明确保留这种边界。
5. **逐步积累完整记忆。** 本步的新认识进入短期记忆，下一步继承为长期记忆；既有认识、未知和形成来源都要保留。
6. **整体地图加逐函数记录。** 函数笔记镜像源码目录，帮助从整体关系回到具体文件和函数。
7. **通过真实模拟持续迭代。** 一起观察使用哪个 skill、读了什么材料、问了什么问题、哪些内容值得保存；展示可能的记录方式，讨论后逐步改进 skill。
8. **要求与讨论持续保存。** 不让记录格式的来由和修改理由只留在聊天里。
9. **给出有使用场景依据的模型。** 包含原仓库实际调用代码、该场景的输入与最终输出、相应上下文，以及 LLM 根据这些材料给出的场景心智模型。
10. **用短例子和短上下文控制负担。** 默认一组小输入输出、几行真实调用代码、简短场景说明和 LLM 模型。完整请求及长解释按需查阅。

以上是明确要求；下面的具体版式和一次聚焦一个细节的节奏是当前执行基线，仍需通过实际互动调整。

## 目录与收录范围

```text
step-N/
├── 02-short-term-memory/
│   ├── overview.md
│   └── functions/<源码相对路径>/<完整函数名>.md
└── 03-long-term-memory/
    ├── overview.md
    └── functions/<源码相对路径>/<完整函数名>.md
```

| 记忆 | 收录什么 | 什么时候写 |
| --- | --- | --- |
| `02` 短期记忆 | 本步新形成或修正的整体关系、相关函数认识与未知 | 随用户实际表述更新 |
| `03` 长期记忆 | 进入本步前，已经由以前步骤积累的完整模型 | 建立新步骤时，从上一步的 `03` 与 `02` 合并得到 |

本步没有发生变化的函数不必再复制到 `02`，仍在 `03` 中保留。同一函数本步有补充时，`02` 中的记录应能独立说明目前已知的作用；合并时保留原有仍成立的认识，不用一个孤立的新句子覆盖旧模型。

没有前序模型时，`03/overview.md` 写“暂无继承”，不创建虚构的函数记录。整体地图与函数索引尚不完整时，可以如实保留不完整状态。

## 每个函数文件：紧凑格式

标题使用真实符号名，类方法使用 `类名.方法名`；开头保留首次接触和最近理解更新。长期记录另注明继承来源。

| 正文项目 | 写什么 |
| --- | --- |
| 我的理解（原话） | 逐字保留用户对函数的直接解释；节选和多次回答分别标明 |
| 使用场景与源码 | 1–2 句话说明当前任务及交接，附几行真实调用 |
| Input → Output | 一组对应的小输入和当前函数的返回值或副作用，标明教学缩减或构造 |
| LLM 根据调用处补充的模型 | 1–2 句话说明职责与边界，明确属于源码解释 |
| 暂时不清楚 | 尚未理解的关系与实现 |
| 来源 | 源码路径、固定版本和行号，样例来源与验证方式，原始步骤的 flow 段落链接 |

原话已经清楚时，省去重复的“当前心智模型”栏目。确需整理零散表述时，可补一句“助手据原话归纳”，不要复写 LLM 模型。

独立模板与已填写案例保存在 skill 的 references 中，按需要读取，不再维护另一份完整模板：

- [短期函数模板](../.agents/skills/repo-reading-memory/references/short-term-memory-template.md)
- [长期函数模板](../.agents/skills/repo-reading-memory/references/long-term-memory-template.md)
- [用户认可的紧凑案例](../.agents/skills/repo-reading-memory/references/translate-function-example.md)

每个实际展开的函数记录提供一个代表场景及对应输入输出，展示方式可以是代码、表格或数据块。默认场景 1–2 句话、调用代码 2–6 行、LLM 模型 1–2 句话；一组小输入输出只说明本轮关心的一处变化。这是控制篇幅的尺度，不为凑行数删掉必要关系。完整请求和长解释留在参考，正文直接显示短例子。

场景终点默认是当前函数的返回值或副作用；若还展示调用者的后续结果，单独标注，避免把后续产物归到本函数。无需同时填写完整异常表、实现分析或掌握评分。仅由助手定位、用户尚未表达认识的符号先列在索引，不冒充已有函数模型。

调用代码必须来自原仓库，保留真实函数名、参数与数据字段，只摘录够用的上下文并标明省略。基类接口要说明具体使用的是哪个实现。输入优先从仓库测试、示例或已知样本缩减，也可构造符合真实接口的最小输入；明确标注教学缩减/构造，并重新核对对应输出。只展示部分输出时标明节选。正文不能只有变量名称，也不默认铺开完整请求。版本与校验过程集中在元数据或来源说明中。

复习模型由 LLM 根据真实调用和输入输出整理，简短说明职责与边界。技术正确性依据源码与验证结果，不依据用户原话或 LLM 自己的断言；设计目的等推断要标明。模型可以据源码先行纠正，用户是否理解修正另记实际状态，不因此更新其认识步骤。

原话保留口语、重复与尚不准确的表达，不把纠正后的句子冒充原话。源码核对与个人理解分开，未知和实际确认状态继续保留在原始讨论中。

共同接口的职责放在定义该约定的符号下，具体协议或后端的差异放在相应实现下。两者互相链接，保留真实源码目录结构。

## 这份记忆怎样形成

助手先准备原仓库调用场景及对应输入输出，请用户用自己的话解释作用，再根据回答逐个追问有助于区分职责、输入输出或交接的问题。结合证据提供 LLM 场景模型；出现混淆时只展开相关源码，解释后请用户说明变化的部分。具体实施细节可以继续未知。

草稿完成后先据源码校对，再按认可样例展示原话、场景、输入输出、LLM 模型、未知和来源，听取用户反馈。展示顺序不改变先听真实复述的互动方式；尚未收到的确认继续留白。实际问答保存在 `04-flow.md`，函数文件保留必要场景及数据并链接原始形成过程。复述和追加问题是形成内容的方法，不要求每个函数再添加一份冗长问卷。长期记忆继承完整条目与证据，无需重复复述旧函数。

试用时每轮只调整暴露出的问题。尚未发生的追问、用户回答和学习效果保持待试用；已写好的示例只说明文件形状，不证明互动方法已经有效。

## overview.md：显示整体模型和函数入口

两层的 `overview.md` 都保留以下内容：

1. **所属步骤与记忆范围**：明确是本步新认识，还是进入本步前的累计模型；长期记忆另写继承来源。
2. **当前整体模型**：已经说清的模块关系。`02` 写本步新增或修正的关系，`03` 写累计关系，不把未讨论的框架全景自动补入。
3. **函数索引**：源码文件、函数记录链接、首次接触步骤、最近认识更新步骤；只定位的函数明确标注尚无个人模型。
4. **尚不清楚**：跨函数或整体关系中仍待解释的部分；局部细节可链接到函数记录。
5. **形成过程**：相关原始步骤的 flow 链接，帮助回到当时的问题。

按需另列“源码场景参考”，链接函数记录中的实际场景与 LLM 模型；与个人整体模型分开，不重复完整代码和样本。

版式分别见[短期整体模板](templates/step/02-short-term-memory/overview.md)和[长期整体模板](templates/step/03-long-term-memory/overview.md)。整体模型、函数索引和过程各有职责，不在 overview 中重复整段函数解释或聊天。

## 继承与更新规则

进入下一步时：

```text
新一步的 03 = 上一步的 03 + 上一步的 02
新一步的 02 = 等待新一步形成的认识
```

按源码位置和符号合并：新函数加入索引；同一函数有补充时整理已有认识，有明确修正时记录修正后的模型并保留出处。未澄清的冲突继续标明，不替用户选一个答案。

- 首次接触步骤一直保留；最近认识更新只随实际理解变化更新。
- 复制、归档、修正排版和移动目录不算认识更新，也不改变掌握状态。
- 形成过程链接显式包含当初发生讨论的步骤名，新写的短期记录也如此。继承后检查解析目标，不让它变成新步骤的同名 flow；普通导航链接不属于形成过程来源。
- 未知随模型继承。只有用户后来明确形成了对应理解，才更新或移除这项未知。
- 用户原话和来源一起继承，校对与实际确认状态从原始 flow 追溯，不能用正文摘要覆盖历史。
- 场景代码、对应输入输出、LLM 模型及其来源和验证方式一起继承，不能在转入长期时丢失使用上下文，也不能改变其作者归属。
- 源码定位保留各自核对的版本，不能把所有旧证据统一改成新的 HEAD。
- 旧步骤保留当时快照；详细原话、提问和纠正放在 `04-flow.md`，助手完整讲解放在 `references/`。

长期记忆表示被后续步骤继承，不表示已经熟练掌握。函数的复习模型由助手据源码整理；个人认识与确认状态只依据实际回答。整体 overview 不把源码解释自动升级为用户已掌握的关系。

## 讨论经过与设计理由

以下按讨论先后整理，均发生在 2026-10-19。这里只记录与长短期记忆有关的要求和选择；更完整的目录方案历史保留在[原始格式讨论](discussions/2026-10-19-step-folder-format.md)。

### 从记录代码，转为记录用户的理解

用户指出，助手应当先帮助定位，再让用户说出自己怎样理解一个模块；具体实现可以留白。因此，函数记录保存的是用户实际形成的模型，完整助手讲解放在参考材料中。这个选择解决了“文档看起来很完整，但并不代表自己理解了”的问题。

### 先确定最少要记住什么

用户提出：

> 1. 哪一个步骤遇到的
> 2. 有什么作用的心智模型

结合此前的实现留白要求，形成了“步骤来源、作用的模型、尚不清楚”三类内容。助手进一步整理出源码定位、首次接触、最近认识更新、当前心智模型、尚不清楚、形成过程六项，并用现有两个 `_translate` 记录试写。六项是具体组织方案，仍可根据回顾是否方便而调整。

### 区分短期新增与长期继承

用户希望当前步骤形成的理解先进入短期记忆，下一步变成长期记忆。由此采用 `新 03 = 旧 03 + 旧 02`：长期保留进入本步前的累计模型，本步补充写在短期中。进入长期表示被后续步骤继承，不等于已经掌握全部实现。

### 从成品示例，继续走向真实问答

用户进一步明确：

> 1. 这个函数究竟完成了什么事情
> 2. 但是形成的过程你需要让我复述一遍
> 3. 你需要问我一些追加的细节问题

> 你需要不断的和我讨论，一遍遍生成可能的结果，不断更新这里的skill才对

这说明仅有文件模板和成品示例还不足以检验方法。当前采用“定位 → 用户复述 → 根据回答追问 → 查看必要证据 → 展示候选记忆 → 讨论调整”。每轮说明准备保留什么及其理由，再听用户指出遗漏或失真。

对于“生成可能的结果”，可以比较不同的记忆组织方式；其中的个人理解仍须取自真实回答。尚未发生的复述和追问不能写成学习历史。

### 先保存专属文档，再继续试用

用户本轮要求：

> 好的请你先保存一份关于长短期内容的专属md文件，我们把要求存放在这里，包括对于这一部分的讨论

因此沿用本文件的已有路径，将其从格式参考扩充为专属要求与讨论文档。现有链接和实例继续可用，后续可在同一位置查看当前规则及其来由。

### 试用反馈：函数记录首先保留用户原话

助手展示了一份整理后的 `_translate` 职责、边界和未知。用户随后指出：

> 我觉得这里首先是需要保留我对于这个function 最直接的表述

此前的函数文件只展示了整理后的模型，原话主要在 flow 中，需要跳转才能看到。根据这次实际反馈，正文新增“我的直接表述（原话）”，放在“当前心智模型”之前，成为七项格式。当前两个函数记录与 skill 示例同步采用；长期继承时一并保留原话和来源。

原话即使包含不准确的字段位置，也保留当时表达；助手把已知问题单独标为待澄清，避免读者将原话误认为已经核对正确的技术结论。这次调整的依据是用户明确的格式反馈，不代表字段理解发生了新变化。

### 候选改法：由 LLM 根据调用处提供职责模型

用户继续提出：

> 我觉得这里是否应该让llm给出一个合理的根据调用处给出的心智模型呢？

助手认为这能补充“当前函数在整条任务链中的位置”。用户原话保留个人认识，LLM 则核对调用者、实参、返回值的使用位置和必要的相邻实现，说明为什么这里需要当前函数、结果接下来由谁消费。源码直接显示的关系与助手对设计目的的归纳需要区分。

以 `_translate` 为例，调用处将 `translated` 和 `tools_schema` 一起交给 `_render_token_ids`。因此助手可以建立“外部协议请求 → 统一消息与工具定义 → 共同 chat template 渲染”的模型；这个下游用途不能仅因助手讲解了，就变成用户已经理解的内容。具体候选模型和源码见[调用处示例](discussions/step-01-translate-preview/references/translation-explanation.md#从调用处建立的候选职责模型)。

当时拟议的展示顺序是：用户直接表述 → LLM 基于调用处的模型 → 二者已经一致与仍待理解的关系 → 形成过程。当时尚未整体改写格式，先将 LLM 模型放在参考材料中。后续采用结果见下一段，前述内容保留其讨论时的状态。

### 已采用：加入真实场景代码、输入输出和 LLM 场景模型

用户进一步要求实际修改格式：

> 1.我觉得需要给一个基于原本代码库的使用场景处的代码
> 2. 给出输入和和最后的输出
> 3. 对应使用的上下文场景
> 3. 给出使用场合的心智模型

这四项在函数记录中落实为“使用场景与调用代码”“本场景的输入与输出”“LLM 基于使用场景的心智模型”，上下文与调用代码放在同一部分。原话仍在正文最前面，个人当前理解、未知和形成过程继续保留。长短期使用同一格式，按原有规则整份继承。

这一版明确输出边界：例如 `_translate` 的返回值是消息和工具定义；下一步产生的 token IDs 属于 `_render_token_ids`。`BaseAdapter._translate` 定义约定，本例的实际转换由 `AnthropicAdapter._translate` 执行。不能把基类占位实现当作有实际转换结果的函数。

两个 `_translate` 实例已按新版补入同一份既有完整请求及其转换结果。该输入源于原页面的教学样本，保留其历史版本；本轮执行当前固定源码提取出的 `_translate` 与四个纯辅助函数核对，两份结果与既有样本一致。验证的是局部转换，没有运行模型、HTTP 服务或完整 Agent。

完整格式示例也保存在 skill 的[配套示例](../.agents/skills/repo-reading-memory/references/translate-function-example.md)，包含短期正文与进入长期时应保留的内容。

### 试用反馈：短例子与简短上下文优先

上一版两个函数记录分别达到 241 行与 246 行，虽然完整数据被折叠，正文仍包含多段重复背景和说明。用户提出：

> 你是否会觉得这里的内容太多了？
> 我觉得是否应该使用一些比较简短的例子呢？
> input output
>
> 场景也是 源代码 给出一个简单的上下文的理解
> 但是上下文本身的解释不应该太长？

据此采用短例子优先：先用一条消息展示真实字段怎样转换，完整消息历史和工具定义作为参考保留。场景和 LLM 模型各用简短说明，校验详情集中到文末，不在每节重复。缩减输入后单独核对返回值，避免将原完整样本的输出套在新输入上。原话、未知与形成来源保持可追溯。
