整理本步阅读目标、入口和核心骨架时使用 [scope skill](../.agents/skills/repo-reading-scope/SKILL.md)；创建或修订本步函数记录时使用[短期 memory skill](../.agents/skills/repo-reading-short-term-memory/SKILL.md)；阅读后的任务链路总结使用 [task-flow skill](../.agents/skills/repo-reading-task-flow/SKILL.md)，以 Step 003 为主要 reference；整体记忆分工与长期继承从 [repo-reading-memory 总入口](../.agents/skills/repo-reading-memory/SKILL.md)进入。skill 的规则与示例可用于其他仓库；本工作流继续负责目标、步骤边界与项目接续。

现行结构是每步一个文件夹：`01-scope.md` 确定阅读范围，`02-short-term-memory/` 保存本步函数记录，`03-long-term-memory/` 保存此前累计的同格式函数记录，`04-flow.md` 保存理解形成过程；阅读后用 `05-task-flow.md` 收拢本步各部分的任务交接、结果和边界。2026-10-20 用户再次明确两层都以单个函数为单位；overview 只做索引，整体主线保存在步骤层。字段统一见[记忆格式规范](memory-format.md)。

新步骤与通用模板采用现行结构。[当前 Step 01](../backlog/repo-reading/step-01-translate-preview/README.md) 是实际例子；已有旧步骤保留当时的目录，不因此重写学习历史。讨论过程见[格式记录](../backlog/repo-reading/2026-10-19-step-folder-format.md)。

scope 采用用户现已确认的阅读目标、指挥官函数、核心骨架三段结构，在其中说明必要前提和停止位置；旧 Step 01 的五项格式保留历史。flow 按实际问题保存用户表述、源码材料、助手提示与后续修正。已形成的认识记入短期记忆，目录和模板调整保存在格式讨论，不混入源码理解主线。

目标是降低阅读负担，同时保存理解怎样变化。最终要留下能够连续读下去的 walkthrough，而不只是文件清单、最终总结或聊天原文。

## 谁来形成和记录理解

认知模型由学习者用自己的话建立。助手先帮助定位当前步骤、相关函数及其在整体中的位置，再请学习者说明“我认为它做什么、为了什么、接收和交出什么”。助手据此整理原话、指出需要核对的关系，并按追问提供源码或解释。

助手持续主动引导：选择下一处值得观察的关系，给必要的局部材料，提出聚焦的问题，听取解释后指出准确之处和需要区分的边界，再共同推进。不能把“认知由学习者表达”理解成只做记录员、等待学习者自行找到全部问题；也不能先给完整答案再要求复述。

两层记忆同时保留个人理解与源码场景，明确区分来源：个人模型只保存学习者已经表达的理解和未知；使用场景、调用代码、输入输出与 LLM 场景模型由助手核对后单列。**“知道这个函数做什么，但不知道它怎样做到”是有效状态。** 用户尚未表达的关系不能由源码解释自动填入个人模型；之后表达了新理解，再增量更新。

函数记录保留够用的真实调用、成对输入输出和简短 LLM 场景模型；完整讲解、扩展分析和教材保存为可选参考，例如步骤外层的 `references/`。这些源码解释不能自动变成个人理解；学习者自己的表述另记。

## 开始一个仓库

1. **先读目标。** 记录为什么读、希望获得什么能力、时间和运行条件。按目标决定哪些模块要深入、哪些先知道职责即可。目标可以是求职、修复问题、接入功能或研究机制，不要求每个仓库都套用岗位路线。
2. **绑定源码。** 沿用已经确认的仓库，核对本地根目录、提交和改动。记录依赖的官方资料及版本。源码变动影响证据时再核对，不把旧行号当成当前事实。
3. **帮助定位初始框架。** 选一个符合目标的真实任务，助手先给足以定位的“输入 → 主要职责 → 输出”线索，再请学习者说当前怎样理解；自己的整体模型按实际表述记录。内部实现允许留白。
4. **另记阅读历史。** 已读过什么、用户明确理解了什么、实际运行过什么分别记录。旧阅读可以帮助选择例子和提醒，不能据此假定整个模型已经建立。

这得到 `000` 起点。本步函数记录先保存在 `02`；`03` 没有前序步骤可继承，初始为空。助手解释和个人表述继续分开，不需要先让读者记住完整架构或通过测验。进入下一步时，再把本步的 `03 + 02` 合并到下一步的 `03`。

## 每一步的目录

```text
steps/step-NNN-<问题>/
├── README.md               # 本步问题、前一步、理解变化与下一问
├── 01-scope.md             # 为什么读、问题、入口、源码范围、边界
├── 02-short-term-memory/   # 本步使用的记录：调取、新增或修正
│   ├── overview.md         # 本步函数索引
│   └── functions/<源码相对路径>/<完整函数名>.md
├── 03-long-term-memory/    # 前序累计模型
│   ├── overview.md         # 累计函数索引与继承来源
│   └── functions/<源码相对路径>/<完整函数名>.md
├── 04-flow.md              # 实际问题、源码材料、用户表述与修正
├── 05-task-flow.md         # 阅读后的任务交接、结果与收束
└── references/             # 按需保留助手讲解或源码参考
```

`01-scope.md` 由助手帮助限定本步位置、问题和材料。`03-long-term-memory/` 完整保留此前形成的理解与未知，`02-short-term-memory/` 保存本步正在使用的记录，包括调取的旧卡与新增、修正。`04-flow.md` 记录实际发生的追问、源码核对与澄清；`05-task-flow.md` 按“本步位置 → 已读部分的交接 → 结果及去向 → 收束与后续衔接”总结，开头保留整体概括，末尾折叠来源。详细教材按需引用；未发生的阅读不预填完成总结。

**按主题组织的项目**：可将上述步骤放在 `topics/<主题>/steps/`。主题只增加问题范围与步骤索引，步骤编号仍按项目内的真实阅读顺序连续；跨主题的“前一步”仍是上一实际步骤，不能因切换目录就清空 `03 + 02` 的继承。

### 函数记录与源码一一对应

以 `slime/ray/rollout.py` 中的 `RolloutManager.generate` 为例，首次形成认识时笔记位于 `02-short-term-memory/functions/slime/ray/rollout.py/RolloutManager.generate.md`，以后继承到相应步骤的 `03-long-term-memory/functions/` 同名路径。

源码的目录层级、文件名和函数名都保留。源码文件在笔记侧用同名文件夹容纳函数记录，类的方法使用完整的 `类名.方法名`；嵌套函数保留外层名称。实际接触哪些函数就记录哪些，不复制整仓目录，也不因打开过文件就标记所有函数已读。无函数的顶层逻辑可记为同一脚本目录下的 `_module.md`，明确它是模块执行过程。

每份函数记录按认可样例先保留用户原话，再给简短场景与调用代码、一组对应输入输出和 LLM 模型，最后列未知与来源。用原话检查理解偏差并据源码纠正；用户是否理解修正按实际回答记录，未知继续保留。标明源码版本、样本来源与验证方式；仅被助手定位的函数可以只留索引，无需预填完整解释。

记录归属按这条认识描述的层次判断：共同接口的职责放在定义该约定的基类或接口符号下，某个协议或后端的具体差异放在实现符号下，并相互引用。任务主线、调用顺序和跨模块交接放步骤 README / scope，flow 保存实际学习问答与修正。不要因为首先通过一个子类认识了共同职责，就把全部共性知识都归给该子类；也不要把某个实现的特有字段当成共同规则。

## 每次接续

先打开该项目入口、唯一进度记录和最近一步的 README，再查看 `03` 的已有背景、`02` 的本步使用记录及 flow 中的未解决问题。按当前问题查镜像目录中的函数记录，不要求每次把全部记忆重新讲一遍。用几句话提醒：目标是什么、目前怎样理解整体、上次停在哪个问题。遇到已读模块，简短唤起职责、输入输出和主线位置；根据具体疑问补充。

从上一轮未解释的交接、读者的新问题或目标需要出发，先与用户讨论本步准备读哪个函数、围绕它弄清什么，以及短期 memory 准备保留哪些认识。助手提出候选函数及理由，由用户确认范围和记录重点后，再展开源码和创建函数记录；不要求预先给出技术结论。用户已经明确指定时直接沿用，不重复询问；改变核心范围时重新讨论确认。目录顺序、旧阅读历史和助手准备的材料都不能代替这次确认。

已有核心骨架时，用 [repo-reading-order](../.agents/skills/repo-reading-order/SKILL.md)推荐下一处入口：先选能回答当前问题的动作，再按需回查它的输入与前置。推荐理由、必要条件和停止位置一起给出；推荐顺序不等于执行顺序，也不等于已经开始新的阅读步骤。

## 一步怎样展开

首轮阅读采用用户确认的[代码阅读指南：剪枝三步法](code-reading-guide.md)：先定位编排函数，提取正常路径，暂时折叠配置、检查、日志与失败分支；沿核心调用下钻不超过两层，弄清交接后返回主线。保留省略范围，实际代码和历史记录不因此删改。

阅读中的记录方式见同一指南的[方法二](code-reading-guide.md#方法二读代码时记录什么)：优先保存数据变化、当前追踪路径、设计疑问及依据，按已有函数记忆和过程记录的分工落盘。

```text
前一步的整体模型
  → 一个需要解释的问题
  → 这次进入哪个模块，为什么
  → 目录 → 文件 → 函数，沿真实调用看输入、行为与输出
  → 回到调用者和任务主线
  → 本步之后的整体模型
  → 下一处尚未展开的关系
```

- **先讨论函数与记录重点，再确认。** 一起确定本步要读哪个函数、解决什么问题、短期 memory 准备保留什么，由用户确认后才创建这个学习步骤并展开函数；未确认前可提出候选及理由，不把准备好的讲解当作已经开始阅读。
- **再继承。** 将前一步的 `03` 与 `02` 合并到新一步 `03`，包括整体地图、索引和函数记录；本步实际需要的旧函数从 `03` 调入 `02`，新读内容也写入 `02`；只有候选或暂未用到的依赖仍留在 `03`。调取保留认识时间与来源，调用处直接链接本步副本。在新步骤 README 链接前一步，scope 标明这次只展开哪里。来自旧版单一 `02-memory/` 的记录可作为前序模型导入，保留原始状态和来源，不修改旧快照。
- **再定位。** 目录说明代码放在哪里；函数及调用关系说明程序怎样运行。每个主要模块记录目录、文件、函数或方法、源码版本，以及为什么在这里进入。
- **先听当前理解。** 定位后先让学习者说该模块做什么、为了解决什么；能描述职责而尚不懂机制时，可以先按接口接回主线。进一步读取实现由当前问题和追问决定。
- **控制新增量。** 一步集中解决一个核心问题。遇到必要前置就先解释它；暂时无关的机制写清职责和后续展开条件，不为凑完整度扩展整套课程。
- **按来源保存。** 函数记忆先列原话，再列真实场景、输入输出及 LLM 模型，末尾提供来源；校对和实际确认状态保留在原讨论中，个人理解不能充当技术结论的证据。`04-flow.md` 保留完整问答和实际澄清。进入长期记忆时整份继承，各部分继续保留作者、版本及验证状态。
- **回到整体。** 邀请学习者说明本步在整体里增加了什么；据实际表述更新步骤 README 中的主线与关系，函数认识更新到相应卡片，overview 只更新索引。缺失关系允许留白，下一步不以填满实现细节为前提。

“逐步增加机制”是讲解复杂实现的方式。除非核对了 Git 历史，否则不能描述成项目当初就是这样逐步开发出来的。

## 怎样保存，避免记录越写越乱

出现新的核心问题并实际展开时，创建 `steps/step-NNN-<问题>/`；同一个问题的追问继续补在本步。起点使用完整文件夹模板，后续步骤先合并前序记忆，再建立本步的范围、过程与空白短期记忆，不能用空白模板覆盖已有模型。记录是一段连贯的解释，不要求每次堆满相同表格或画图。

前一步保留当时的认知快照。后来发现错误，在新步骤写清“原先怎样理解、哪里不成立、依据是什么、现在怎样理解”，并在旧步骤加纠正链接；不要悄悄改成仿佛一直理解正确。普通错字和坏链接可以直接修正。

各仓库只保留一处当前进度。项目入口链接这处进度及步骤目录，章节、网页和模板不维护平行状态。步骤是当时的理解记录，不因创建了文件就被标记为已读、已理解或已运行。

合并后保留原有来源，本步变化写入 `02`，不把同一份前序模型在本步 `03` 中同步改写，也不批量改写旧步骤。复制或排版不算认识更新。源码本体使用固定版本引用与必要摘录；换版本时逐项记录重新核对的接口，不批量把旧证据改标为新版本。

Hugo 正文与认知步骤需要发布同一段内容时，采用同一维护来源或明确引用。完整记忆快照是用户要求保留的学习版本，各步骤可以不同；它与同时维护两份声称“当前”的正文有区别。公开页面保留技术问题、推理过程和源码证据；私人目标、完整招聘文本或个人状态按项目约定保存在仓库记录中。

## 助手每轮的最小动作

开始时读取方法与项目接续，帮助定位一个适当大小的模块；先听学习者的职责理解，再按需要核对代码；结束时忠实保存实际表述、留白及下一步。提问用于共同构建模型，不是背诵考试或继续阅读的门槛。

用户已经授权持续记录这类理解过程时，按这个工作流直接维护。不要求用户反复提醒目标、阅读历史或“把刚才的解释也记下来”。
