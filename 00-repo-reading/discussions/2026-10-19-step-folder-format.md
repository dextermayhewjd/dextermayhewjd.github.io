## 当前判断：可行，三个部分分别回答三个问题

| 用户的划分 | 回答的问题 | 建议保存的内容 |
| --- | --- | --- |

| 1.2 截至本步的完整记忆 | 到这里，我怎样理解整个系统和每个接触过的函数？ | 当前整体模型、全部已涉及目录/文件/函数索引、逐个函数的理解、尚未解释的关系 |
| 1.3 本步代码与交接 | 当前这些函数怎样一起完成工作？ | 本步使用的真实代码片段、调用顺序、具体输入输出结构、状态变化，以及返回主线的位置 |

1.1 是本次阅读的入口；1.2 是读完这一步后留下的累计模型；1.3 是这一步怎样从代码得到新理解的过程。

同一个函数会同时出现在 1.2 的理解记录和 1.3 的当前调用中。前者保存对该函数已建立的解释，后者保存它与其他函数在本步如何配合；不必在 1.3 重抄整份函数说明。

## 建议目录：累计记忆拆为整体地图与函数记录

```text
repositories/<repo>/
├── README.md                       # 阅读目标、唯一进度入口、步骤索引
└── steps/
    ├── step-001-<本步问题>/
    │   ├── README.md               # 本步问题、上一步链接、这次理解变化
    │   ├── 01-scope.md             # 1.1：只列本步需要看的代码
    │   ├── 02-memory/              # 1.2：截至本步的完整记忆
    │   │   ├── overview.md         # 当前整体模型、目录/文件/函数索引
    │   │   └── functions/
    │   │       └── <源码相对路径>/
    │   │           └── <完整函数名>.md
    │   └── 03-flow.md              # 1.3：本步真实代码、调用和输入输出
    └── step-002-<下一步问题>/
        ├── README.md
        ├── 01-scope.md
        ├── 02-memory/              # 从 step-001 的 02-memory 完整复制，再更新
        └── 03-flow.md
```

这里的 `functions/<源码相对路径>/<完整函数名>.md` 以源码位置组织。例如 `functions/train.py/main.md` 与 `functions/slime/ray/rollout.py/RolloutManager.generate.md`。目录中的 `train.py` 用来映射原始文件，不是另一份可运行脚本。

这只是格式示意，不表示已经读取这些函数，也不要求现在创建全部目录。实际接触一个函数时才创建相应记录。

讨论时另一个候选格式是把 1.2 全部写入 `02-memory.md`：文件少，起步简单；函数多时会变长，单独更新与查阅更费力。用户随后选择目录形式，并要求与源码文件夹结构一致。

## 1.1 怎么写：只保留本步的阅读范围

开头用两三句话说明：从上一步的哪个缺口继续，这次解决什么问题，读到哪里就足够。然后用一张小表定位。

| 目录 | 文件 | 本步涉及的函数 | 为什么涉及 | 接触方式 |
| --- | --- | --- | --- | --- |
| 相对源码根目录的路径 | 真实文件名 | 完整函数或方法名 | 对本步问题的作用 | 新增展开 / 重访 / 只引用 |

不列与本步无关的整个文件夹，也不因为打开了一个脚本，就把其中所有函数记成已读。只引用了某个函数时，可以先留在索引，标记内部尚未展开。

## 1.2 怎么写：整体地图与逐函数理解同时保留

`overview.md` 保留一份在当前步骤可独立阅读的整体模型：任务从哪里来，经过哪些主要职责，结果交给谁。列出截至此处已接触的目录、脚本、函数及其理解记录链接，并标明哪些只知道接口、哪些已看过某一条分支。

它的重点是“目前怎样理解”，历史上发生过什么疑问或纠正则在对应步骤的说明中保留。这样既能从当前快照接续，也能回到旧步骤查看理解如何变化。

每个实际展开的函数有一份自己的记录，建议采用以下格式：

```markdown
# <完整函数名>

源码：<相对路径、固定提交、行号或链接>
首次接触：<步骤>；最近更新：<步骤>
已展开的范围：<例如正常路径；某分支尚未阅读>

## 为什么有这个函数
它承担什么责任？上一层为什么会调用它？

## 输入
真实参数名、类型或关键字段、值从哪里来。
必要时给一个最小数据示例；类型提示不充分时明确尚未确定。

## 它实际做了什么
按需要解释关键行为、调用和状态变化；不逐行翻译无关代码。

## 输出与交接
返回什么类型和字段？谁使用结果？
没有返回值时，写明状态修改、文件、网络请求等有关副作用。

## 当前理解与未解决问题
读者明确说过的理解、助手给出的解释、代码核对结果分别标注。
保留仍不确定的部分，不把助手的解释自动写成读者已经掌握。
```

函数目录索引只负责找到记录。不能用一行“用于初始化”代替已经展开过的完整解释；也不要求为没有展开的内部机制编造说明。

## 1.3 怎么写：让数据把本步的函数连起来

先画一条本步调用关系，再围绕关键交接给出真实字段或类型：

```text
调用方持有什么输入
  → 传给当前函数哪些参数
  → 当前函数怎样调用下一层或改变状态
  → 返回什么结果
  → 调用方怎样继续使用这个结果
```

| 交接 | 传入什么 | 取得什么 | 谁接着使用 |
| --- | --- | --- | --- |
| 实际调用方 → 被调用函数 | 关键参数、类型和数据形状 | 返回值、类型和字段，或有关副作用 | 后续函数或调用方下一行逻辑 |

只摘本步用到的代码，保留真实函数名和字段名，并指向固定版本原文件。裁剪处说明省略了什么。复杂时用一个贯穿输入与输出的小例子；示例值要标明是教学值。

遇到异步调用，要区分立即取得的对象和等待后取得的结果；遇到回调、队列或跨进程交接，也应写清实际接收方。按当前问题解释，不提前展开整套并发课程。

## 下一步怎样继承 1.2

以第 2 步为例：

1. 从第 1 步结束时的 `02-memory/` 完整复制到第 2 步。这包括整体地图、索引和已有函数解释。
2. 为第 2 步建立新的 1.1，列出这次真正需要看的代码；第 1 步出现过但这次没用的函数仍保留在累计记忆中。
3. 在第 2 步的 1.3 中沿输入、行为、输出讲解新问题。
4. 在第 2 步的 1.2 中更新相关函数解释、增加新函数并修正整体关系；其他理解原样继承。
5. 在第 2 步 README 中简记新增或修正了什么，并链接关键疑问与证据。

第 1 步继续保留当时的模型。后来发现错误，在新步骤说明旧理解和修正依据，并给旧记录加纠正链接；不会把后来的理解倒写成当时已经知道。

复制的是学习记忆，不要求复制整个源码仓库。函数记录中的源码提交随证据保存：换了源码版本，逐项说明本次重新核对了什么，不能只把所有旧记录的版本号一起替换。

## 这个方案的成本与边界

- 每步的累计记忆会重复，占用一些空间，也会使文件数增加；换来的好处是任何一步都有完整的理解背景，适合回看和比较。
- 新步骤从上一份复制后，只改本步真正改变的部分。旧步骤作为历史快照，不需要同步维护所有副本；当前进度仍只在项目约定的位置记录。
- 先用 Markdown 和文件夹手动验证格式，不为这轮讨论新增数据库、自动生成器或校验系统。等真实步骤暴露重复劳动，再决定是否自动化复制和索引。
- 格式确认后，原 `000-initial-model.md` 已迁入 step-000 文件夹的整体地图，旧入口保留跳转。本次没有把旧讨论补写成已经完成的多个步骤。

### 以等待 Harness 的一段为例

当前源码中，generate 等待 `HARNESS_CLS().run(...)`，得到 `agent_exit_code` 后才执行 `swe.git_diff(...)`。已有导览同时说明：CLI 在沙箱中运行时会请求 Adapter，Adapter 再与模型服务交互。这些 HTTP 交互不能画成 generate 顺序调用的一串普通函数。

因此，这段 `03-flow.md` 至少需要让读者回答：

1. 外层目前停在哪个调用，后面的哪一行还没发生？
2. 等待期间是谁在工作，跨越了哪些运行边界？
3. 什么结果让外层继续，这个结果交给谁使用？

`BaseHarness.run` 的函数记录则说明它如何接收 `sb`、工作目录、Session 身份、Adapter 地址、预算和 prompt，并最终交回退出码。它不需要承担整段任务交互的所有说明。

### 这个例子暴露出的四条整理原则

- **学习步骤按问题划分。** 一步可以涉及几个函数，同一个 generate 可以在多个步骤中逐渐展开；每步增加一个明确关系，而不是强制一函数一学习步骤。
- **目录定位与运行关系同时保留。** 函数记录按源码位置找，流程正文按实际交接读；调用、等待、HTTP、循环和返回不能混成同一种箭头。
- **函数理解包括状态与生命周期。** 例如 `open_session` 注册的会话，后续请求会使用，`finish_session` 会导出，`drop_session` 负责清理。这类关系需要记录共享状态及其使用者，不能只看当前函数的返回值。
- **完整记忆用于续读，主阅读仍有重点。** 每步先读当前问题和必要的整体提醒，再读 `03-flow.md`；需要解释某个函数时查对应记录。复制完整记忆不等于每步重新读完所有函数。

## 从记忆与心智模型角度选择入口和步长

用户继续提出：理解 Coding Agent 时，可以先读 Adapter 的 `_run_turn()`，理解消息与工具定义的转换；步子应当不大不小，太小会慢，太大会不知道在做什么。

本节保存针对这个例子的讨论建议，尚不据此改变 Slime 当前阅读接续，也不把下面的示意单元记作已经完成。

### 先区分整个任务与一次请求

`BaseAdapter._run_turn()` 负责一次模型请求：接收请求、转换输入、调用模型、处理输出、组织响应并记录这一轮。具体消息与工具定义转换由协议子类的 `_translate()` 承担。

如果问题是“整个 Coding Agent 怎么工作”，先用很短的主线定位任务、CLI、模型请求、工具执行和结果收集；工具循环由 CLI 推进，不能把一次请求的 handler 当成整个 Agent。如果问题已经缩小到“一次模型请求怎样接入”，则可以从 `_run_turn()` 进入。

不要求先逐行读完全局入口。这个短定位只负责说明：请求从 CLI 来，经 Adapter 接到模型服务，再把回复交还 CLI；局部阅读后要能回到这条关系上。

### 第一小步可以覆盖一个完整的转换问题

建议问题是：**请求 body 里的消息和工具定义，怎样变成内部要使用的消息列表与工具 schema？**

在固定源码 `2f2318653f6f794dddd321eff7c9d4b7b174643f` 中：

- `slime/agent/adapters/common.py:341`：`_run_turn()` 用 `self._translate(body)` 取得 `translated, tools_schema`。
- `slime/agent/adapters/anthropic.py:58`：`AnthropicAdapter._translate()` 分别调用 `_translate_messages()` 和 `_tools_to_chat_tools()`。
- 同文件第 81、123 行：两个转换函数定义。它们属于同一个输入转换问题，可以一起看必要路径。
- `common.py:342`：随后调用 `_render_token_ids(...)` 使用转换结果；本步先知道结果交给谁，token 渲染内部留待下一问。

本步可以用一份“用户消息加一个工具定义”的请求走通普通转换路径，再根据实际疑问展开历史工具调用与工具结果。请求已经过哪些预处理、Session 在哪里取得，需要在开头标明位置；不用同时下钻所有生命周期机制。

转换工具定义并不执行工具。这个职责区别应在本步说明，避免把后续 CLI 的工具执行归给转换函数。

### 怎样判断步子是否合适

| 粒度 | 这个例子里的表现 | 调整方向 |
| --- | --- | --- |
| 太小 | 一个读取字典字段、一个列表遍历各建一个步骤，单独看不出完整作用 | 合并到能解释一份输入如何得到输出的单元 |
| 合适 | 沿一份 body 解释消息和工具定义的转换，知道输出形状与下一接收方 | 保留这个完整问题，根据卡点补必要前置 |
| 太大 | 一次展开整个 `_run_turn()`，同时处理转换、token、模型调用、解析、响应、轨迹与清理 | 先定位完整骨架，再按具体交接分段 |

用函数数量或代码行数统一切分会失真。建议用一个可解释的问题划界：输入是什么、这一段改变什么、输出交给谁？一个步骤可以涉及多个短函数；同一个长函数可以跨步骤逐渐展开。

如果读者已经能解释某个普通语法，只需提醒，不重复开课；若某个新对象或前置关系导致无法跟上，就先补这一处，再返回当前转换问题。具体步长由真实反馈修正，不以固定数量或时长作保证。

### 文件记忆如何帮助形成自己的理解

完整 `02-memory/` 保存可恢复的理解背景；每轮仍只阅读当前相关的一小部分。函数记录标出“当前解释到哪一段、哪些部分尚未展开”，以后在复制出的新记录里继续补充，避免第一次就填满整个函数。

建议每步结尾留一个可选的短复述，例如：“一份 CLI 请求里的工具定义经过这里之后，变成什么，谁继续使用它？”允许看提示、卡住后回查，不把复述当作继续阅读或承认已读的前置条件。助手只能按实际回答记录理解，不把保存文件等同于读者记住。

这个设计参考了 Karpicke 与 Blunt 在科学文本学习中比较主动回忆与概念图学习的实验：主动提取、重建所学内容可以帮助理解性学习。[原始研究](https://learninglab.psych.purdue.edu/downloads/2011/2011_Karpicke_Blunt_Science.pdf)。把短复述用于源码阅读是本工作流的应用建议；该实验没有验证 Slime、某种目录格式或最合适的单步长度。

### 进入下一步时如何交接

```text
第 N+1 步的 03 = 第 N 步的 03 + 第 N 步的 02
第 N+1 步的 02 = 留待新一步逐渐形成
```

这里的加号表示按整体关系和具体函数整理、合并，不是把两个目录简单拼接：

1. 复制上一份 `03` 的累计模型到新一步 `03`，保留完整记忆。
2. 将上一份 `02` 的新增认识纳入对应整体地图和函数记录；同一函数有补充时合并，有明确纠正时采用已确认的修正并保留来源。
3. 未知和留白一并继承，不因移入长期记忆就自动补成答案。相互矛盾但尚未澄清的认识，继续标明待澄清。
4. 新一步的 `02` 开始为空，随后只记录这一步由用户表达的新认识；旧步骤保持当时的样子。

第一步没有前序记忆时，`03` 可以明确写“暂无”，不用编造内容。这保留了用户原先要求的完整继承，同时让本步变化可以单独阅读。

“短期”“长期”在这里是文件职责：本步形成、后续继承。归入长期记忆不等于用户已熟练掌握、无需提醒；尚不清楚的实现仍然尚不清楚。

## 01 scope 与 04 flow 的职责规范

用户反馈短期与长期记忆的分工已经比较清晰，进一步提出需要规范 `01-scope.md` 与 `04-flow.md`。在看到以下分工后，用户确认：“那么请这样子修改一下吧”。本规范已用于 Step 01 的两份正文；其他旧步骤与通用模板尚未迁移。

### 两个文件分别回答什么

| 文件 | 核心问题 | 建议写入时机 | 与记忆的关系 |
| --- | --- | --- | --- |
| `01-scope.md` | 为什么现在读这里，本步从哪里开始、读到哪里？ | 开始本步时由助手帮助定位；追问确实改变范围时说明调整 | 引用已有模型，只写进入条件和阅读边界，不重复本步结论 |
| `04-flow.md` | 围绕这个问题，怎样从源码观察和讨论形成或修正理解？ | 随实际阅读和对话逐段增补 | 保存结论的来由；得到用户表述后，再把认识整理进 `02` |

`04-flow.md` 仍要连接真实代码、输入输出与交接；单独按聊天轮次堆原话，容易失去代码主线。助手先给必要定位和材料，用户表达自己的认识；尚未得到用户回应的解释，保留为助手提供的材料或待确认关系。

### 01 scope：五项最小约定

1. **为什么进入这里。** 接上一步模型中的哪个问题；第一步可直接写当前任务情境，不编造前序理解。
2. **本步核心问题。** 写具体的技术问题，例如“请求转换返回哪两类信息，共同约定与具体 Adapter 怎样分工”；避免仅写“理解这个模块”或“让用户复述”。
3. **入口与暂时接受的条件。** 写已知输入、当前调用位置，以及本步暂时不追问的来源。例如“已取得 body”，要标成场景条件，不自动算作用户已理解 HTTP 接收过程。
4. **本步源码范围。** 只列必要目录、文件、函数、源码版本与接触深度；区分展开、重访和只定位，完整分析放在参考中。
5. **本步读到哪里。** 说明希望看清的职责或交接、返回哪条主线，以及允许继续留白的实现。它用于控制阅读量，不是通过复述考试后才能继续的门槛。

已知模型优先链接 `03`；若是进入本步前的临时表述，可保留一句并注明当时状态。不能随着讨论推进，把后来才形成的结论倒写成开头已经知道。范围确实随用户追问改变时，简记原因和新增范围即可，不要求预先锁死所有问题。

### 04 flow：按问题组织实际走过的过程

开头只保留能接回 scope 的局部定位。随后每段围绕一个实际发生的问题，按需要包含：

- 用户当时如何解释，或具体卡在哪里。
- 为澄清这一点实际查看的源码、数据形状或调用关系；必要时给短片段并标注来源，长解释链接 `references/`。
- 助手提供了什么提示、区分或纠正。
- 用户之后如何表述；尚无回应就保留待确认，不能写成已经形成的认识。
- 由此可进入 `02` 的认识，以及仍然未解决的部分。

这些是内容约定，不要求每条聊天都填一遍五栏。简单关系可以一段写清，只有出现混淆时才展开来龙去脉。局部代码的输入、行为和输出用来支撑理解过程；运行顺序与讨论顺序应分别说明，不能因为先讨论 common 就声称程序先执行 common 的接口方法体。

末尾简记本步改变了哪项认识并链接 `02`，保留真正未解决的问题。目录迁移、模板命名与 skill 设计的讨论放在本格式讨论文件，不混入源码学习主线；相关历史可以链接回来，不必删除。

scope 可以用“已经拿到请求 body”为进入条件，围绕 `_translate` 的输入输出和共同约定选择相关文件；token 渲染、模型调用与转换的具体规则仍可在边界之外。

flow 应保存已经实际发生的这条理解演进：

```text

  → 说明两份结果分别保存对话历史与工具定义
  → 提出共同认识应当归属 common 的问题
  → 区分 common 的约定与两个 Adapter 的具体实现
  → 具体转换机制继续留白
```

这是一条讨论和认知演进，不是函数运行顺序。用户已经表达的稳定认识仍在 `02`；`01` 提供进入这条主线的范围，`04` 保存认识怎样形成。上述示范没有增加用户尚未表达的技术结论。

## 短期与长期记忆：最小记录内容

2. 有什么作用的心智模型。

### 建议保留三类内容

| 内容 | 记录什么 | 为什么需要 |
| --- | --- | --- |
| 步骤来源 | 首次在哪一步接触；认识发生实际补充或修正时，记录最近更新步骤，并链接相应 flow 段落 | 既能找到最初遇到的位置，也能找到当前认识的依据 |
| 当前心智模型 | 用户已经说明的作用、目的和关系；输入输出、调用关系或实现只写已经说明的部分 | 让后续能够恢复“我目前怎样理解它”，不只保留模糊标签 |
| 尚不清楚的边界 | 具体哪些问题或实现仍未理解 | 避免后续助手把知道职责误认为已经掌握整个函数 |

函数身份沿用现有目录、文件标题和源码定位，不额外增加一套编号。整体地图仍在 `overview.md`，逐函数认识仍按实际源码路径组织；这里规定的是每份记忆最少要保存什么。

“哪一步遇到”与“哪一步形成了当前认识”可能不同。首次遇到某函数时只知道位置，后面才理解返回值，再后面才理解实现。首次接触步骤保留原值；只有认识实际变化时才更新最近步骤。必要时给不同认识分别链接其形成时的 flow，不为每次复制、重新打开文件或纯排版修改制造一次理解更新。

### 同一格式用于两层记忆

## 继续试用：通过复述与追加问题迭代格式

用户在 skill 建立后进一步要求：

> 1. 这个函数究竟完成了什么事情
> 2. 但是形成的过程你需要让我复述一遍
> 3. 你需要问我一些追加的细节问题

> 你需要不断的和我讨论，一遍遍生成可能的结果，不断更新这里的skill才对

这次反馈暴露的不足是：上一轮完成了存放格式与继承规则，并给出了现有认识的成品示例；但尚未通过与用户真实复述、追问和审阅候选记录的一轮互动，检验提问和最终文件是否适合使用。之前的静态检查与独立案例验证继续成立，但不证明用户的学习效果。

### 本轮先采用的方法

- 使用 `repo-reading-memory` 引导一次真实的函数认识记录；使用 `skill-creator` 指导规则维护。用户与助手的实际互动用于判断学习方法，不由助手或测试代理代演用户回答。
- 函数记录沿用六项基线；“当前心智模型”首先回答究竟完成什么事情。复述、追加问题及其理由、源码材料和认识变化放在 flow，记忆通过链接追溯。
- 助手先定位，再请用户复述，随后根据回答每次追问一个有用的细节。遇到混淆则核对源码，再听用户如何修正；没有回答的部分保持待回应。
- 基于实际回答展示候选记忆，说明保留和留白的原因，再依据用户反馈改写。格式建议可作为草案，不能编造“用户可能会回答”的内容并保存成个人模型。
- 及时将明确规则写入 skill；本轮尚未试过的学习效果不标为验证完成。历史理解与来源继续保留，不因修改方法而重置。
