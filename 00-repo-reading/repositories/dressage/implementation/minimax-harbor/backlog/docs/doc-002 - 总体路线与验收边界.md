# 总体路线与验收边界

[项目目标](../../README.md) · [已确认决策](../decisions/decision-001%20-%20先完成无-GPU-API-评测链路，再接-Agent-Sandbox.md) · [迁移原文](doc-001%20-%20迁移前原文快照.md)

本页是分阶段工作清单，尚非已经核准到逐文件的补丁设计。按实际依赖调整局部顺序；第一阶段验收必须包含 Slime 发起，不能以独立 API 测试脚本代替完整闭环。

## 第一阶段：MiniMax API 跑通 Harbor 路线

| 工作项 | 要解决的问题与候选位置 | 验收条件 |
| --- | --- | --- |
| A. 开发基线与启动核对 | 从固定提交建立开发分支；检查 Python >=3.12 / Harbor 0.18.0 门禁；明确使用未初始化的 Slime 子模块 aaf5c209 还是独立 checkout；检查 Slime `train.py` 与 Dressage 启动配置 | 固定依赖选择，列出无需 GPU 的启动方案、阻碍和第一条验证命令；不自动升级 Harbor |
| B. 最小 MiniMax 客户端 | 新增独立客户端的具体路径待设计；核对模型、Base URL、消息、tools、认证、超时与错误 | 先用模拟响应验证协议处理，再真实验证文本回复和工具调用→工具结果→继续回复；两类证据分开 |
| C. 模型请求及结果接入 | 先验证 rollout 模式下 `trajectory.require_trainable_tokens=false` 的完整结果合同（不视为整个 API 适配已完成）；优先评估 `dressage/proxy/server.py` 的消息边界；核对 `integrations/harbor/artifacts.py` 的 finalize/read/commit | Agent 能收到正文/工具调用；记录能完成；不伪造 token、logprob 或权重版本；原 SGLang 路径的相关检查继续通过 |
| D. Slime 发起与完整任务 | 根据 A 的结论适配实际入口；使用一个固定 CPU 任务、一个 Agent、一个可用环境后端 | 从 Slime 发起，无本地模型/GPU，完成任务、评分、结果返回、日志产物保存与资源清理；再验证一次关键失败或取消 |

B/C/D 可以拆成独立小验证，但不能把其中任一项的成功报告成全部接入完成。对每项先明确“原行为、拟改变的行为、涉及文件、验收方法”，再修改代码；不按看到的函数数量决定改动范围。

## 第二阶段：替换环境为 Agent Sandbox

| 工作项 | 验证内容 | 收尾证据 |
| --- | --- | --- |
| E. 后端适配 | 保留基线的模型、Agent、题目与评分配置，接通 Harbor Environment 与 Agent Sandbox | 创建/领取、就绪、命令执行、文件上传下载、日志产物与停止正确交接 |
| F. 代表性任务 | 一个最小任务、一个依赖特定环境的代码任务、一个失败或超时用例；优先复用前阶段用例 | 任务配置、评分结果、失败分类、支持/不支持能力清单；不以覆盖全部 benchmark 为目标 |
| G. 预热与并发 | 冷路径后验证热领取；观察池命中、耗尽和补充行为；在本机承载范围内少量并发 | 镜像/环境匹配、结果归属、等待耗时、资源所有权与清理检查；不预设性能数字 |
| H. 排障与复现 | 围绕上述运行定位镜像/启动/执行故障，检查取消后的残留资源 | 具体故障的事件或日志、定位过程、处理结果，以及可重跑的版本/配置/命令 |

E–H 是上方已确认目标的验收拆分，不是新增四套平台。数量和并发度按本地资源确定；对同一用例复用日志和验证证据，避免重复建设。

不把迁移 Dressage 原生 PrewarmStore 作为前置，也不把 ACK/OpenKruise 后端当成 kubernetes-sigs/agent-sandbox 已完成的适配。

## 本轮不做

- 不下载任意模型来凑齐初始化，不进行本地训练或权重同步。
- 不重写 Harbor Job/Trial 调度，不同时改造原生 blackbox 路线。
- 不重新通读三个仓库，不在缺少真实测试时声称性能提升或模型更强。
- 不自研调度器、镜像存储或任意状态快照，不将千级并发、所有 benchmark、多容器或 GUI 支持作为本轮要求。
- 不把 SDK 作为本轮必交付物；无 GPU/API 实验不宣称已完成真实策略训练与权重更新。

## 任务与总体路线的分工

本页保留 A–H 总体阶段和验收边界，不单独更新任务状态。Q04 → MH-001；Q01–Q03 也已迁入任务。具体实施计划在任务开始后填写；未展开的后续阶段不自动创建任务。

## 链路稳定后的候选工作：SDK 封装

用户希望最后了解并评估 SDK。先完成真实调用与结果验证，再确定调用者、复用接口、配置、错误及资源清理合同；不预先新建 SDK 或网关。具体范围在[十点判断与 SDK 议题](../../../references/implementation-scope-assessment.md)中记录，尚未形成接口设计或发布承诺。

## 共用验收记录要求

不增加独立平台模块，在原工作项内补齐：

- 运行清单保存实际代码/镜像版本、任务、模型、采样参数、预算、评分规则和失败类别，支持再次执行与分析；远端输出不承诺逐位复现。
- 通过已有扩展接口换一个任务配置或评分规则，不改核心执行循环。
- 有限并发下验证 Trial 结果归属，覆盖超时或限流、取消与资源清理；核对已有重试层数和调用放大。
- SDK 是最后的候选封装，当前不新增通用调度网关或内存快照系统。
