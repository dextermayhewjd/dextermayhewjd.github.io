## 三轮复核结论（2026-11-17）

**原十点适合作为本次项目主线，但不能当成岗位能力的完整证明，也还不是可以直接编码的完整设计。** 保留先 MiniMax API、后 Agent Sandbox 的顺序；需要修正版本前提、优先复用现有配置，并把工程验收补具体。SDK 保持最后评估。

### 第一轮：核对技术事实与源码边界

| 核对点 | 证据与判断 | 处理 |
| --- | --- | --- |
| Harbor 版本不是随便选 | `compat.py:37` 的 require_harbor_runtime 强制 Python >=3.12、Harbor 恰为 0.18.0 | 先检验支持版本；0.25.0 的阅读结论保留，不冒充可直接运行 |
| 实际 Slime 基线尚未统一 | Dressage gitlink 固定 `aaf5c2092b01219fa0d5c2d323741d409086ca32`；`git submodule status slime` 带 `-`，本地子模块未初始化。官方训练脚本默认 SLIME_ROOT 指向该目录；此前独立 checkout 为 `18868a79` | 运行前显式选定路径、提交和导入来源；此前 train.py 结论仅直接适用于独立 checkout，不能自动外推到未读的子模块版本 |
| 结果层已有配置可复用 | `TrajectoryConfig.require_trainable_tokens` 默认 true；training 模式强制 true；`validate_attempt` 只在开关为真且训练 token 数为零时追加对应失败 | 优先核对 rollout 模式和配置关闭后的完整合同，不能预设必须重写 ArtifactStore。其他字段与 finalize/read 协议仍待验证 |
| 消息入口不是现成通用后端 | pipeline 读取 messages/tools，但 create_app 初始化 tokenizer，生成和记录仍依赖 token 结果 | 消息边界仍是候选，不承诺“改一个客户端即可” |
| Agent Sandbox 不是隔离内核 | 官方说明其管理 Kubernetes 资源，并通过 RuntimeClass 委派底层隔离 | 不重复造运行时；选择后端时核对真实隔离与兼容性 |
| 本地 kind 不是生产仿真证明 | 官方将 kind 定位为测试和本地开发工具 | 可验证功能与故障处理，不能据此承诺千并发、生产可用性或相同隔离性能 |

另外，原始材料中“gVisor 等于每个沙箱一份 Linux 微虚拟机内核”“K8s 只能运行无状态应用”“固定并发数必然打挂”等表述不能采用。gVisor 是用户态应用内核；Agent Sandbox 官方本身就在管理有状态 Pod。未核验的产品快照能力、发布时间和市场采用率继续留在原文，不进入需求。

### 第二轮：按用户提供的 JD 检查缺口

本项目重点对应模型/工具调用、任务执行、上下文、Trace、结果评测、异步并发及集群运行。JD 没有要求个人实现一整套云沙箱平台，也不能据它推出雇主一定采用 Agent Sandbox。

在已有流程中补下面的验收，不另增加整套课程：

- **可扩展**：主线跑通后，演示替换一个评分规则或任务配置，不改核心执行循环；先沿 Harbor 已有接口完成，不要求自研 Agent 框架。
- **可复现与可分析**：保存任务标识、仓库/镜像版本、模型标识、实际采样配置、运行预算、评分规则、请求归属和失败类别。可重跑不等于远端模型输出逐位一致。
- **并发与稳定性**：小规模并发验证互不串结果；覆盖 API 超时或限流、任务取消及资源清理。检查已有重试位置，避免多层重试重复放大请求；强制进程退出不依赖 finally 必达。
- **训练知识边界**：保留已读 rollout→reward→训练数据的解释能力，说明 API 评测缺少哪些训练资料；不把本项目包装成真实 PPO/GRPO 训练验证。
- **owner/协作的可展示证据**：让需求、设计理由、测试、故障复盘与运行说明能够被别人使用；项目不能独自证明真实团队协作经验。

### 第三轮：实施顺序与 SDK 是否值得做

1. 先做版本/路径、无 GPU 启动与结果合同的最小可行性核对，范围是找到最短路径，不先重写整个训练入口。
2. MiniMax 独立请求验证与上述静态核对可并行准备；完整验收仍是从 Slime 发起并接回 Harbor 结果。
3. 单任务通过后，再补有限并发、一个扩展例子及关键异常验证；之后切换 Agent Sandbox，比较环境行为与冷/热启动耗时。
4. SDK 放在真实使用方式稳定后。优先使用现有配置与适配器；若调用者确实需要一组重复的操作，再提炼为可安装 Python 包、清晰的异步接口与样例。不要先造独立 Sandbox Manager、通用 RPC 平台或公开 PyPI 包。

这些是复核后的建议与验收细化，不代表新能力已完成。下一步以现有 plan 的 A 项、issues 的版本与启动问题为准。

### 结论分级

- **必须保留**：API 与工具闭环、结果正确性、从 Slime 发起、Harbor 复用、必要的故障清理、K8s 实际部署与排障。
- **需要调整**：先统一 Slime/Harbor 版本；先验证现有结果配置；补可复现与扩展性验收；本地指标如实限定规模。
- **后置学习**：小规模预热、稳定接口的 SDK 封装。
- **不列入当前目标**：重写调度器、分布式镜像存储、MCTS 全内存快照平台、千并发 SLA、独立通用网关平台。

核对来源：[Agent Sandbox 官方说明](https://github.com/kubernetes-sigs/agent-sandbox)、[gVisor 的定义](https://gvisor.dev/docs/)、[kind 设计原则](https://kind.sigs.k8s.io/docs/design/principles/)；本地 Dressage 固定提交下的 `.gitmodules`、gitlink、训练脚本、`compat.py`、`config.py` 与 `artifacts.py`。三轮分别为事实核对、岗位覆盖和实施/接口审查，不是三次运行实验。[复核前快照](history/2026-11-17-scope-before-three-pass-review.md)保留原表述。

## 十点判断

**核心目标：做出可运行、可排障的 Agent 评测链路，暂时不自建完整沙箱平台。**

1. **先纠正原始材料中的范围膨胀**
   - “95% 都用商业沙箱”“上千并发必然打挂 K8s”“本地能 100% 复刻生产”不能作为已确认依据。
   - 用户提供的 JD 没有要求独立开发调度器、存储系统和完整商业沙箱。

2. **明确最终交付什么**
   - Dressage fork 中的 MiniMax 接入代码。
   - 从 Slime 发起、经过 Harbor 的完整任务。
   - 测试、运行配置、结果记录与排障说明。
   - 后续增加 Agent Sandbox 环境适配。
   - 独立 SDK 不是首轮闭环的前置；用户现希望在最后评估和学习其封装方式，见下节。

3. **当前先解决模型接口**
   - 从哪里接收 messages/tools。
   - 怎样调用 MiniMax、接回回答和工具调用。
   - 怎样处理超时、错误、用量和多轮上下文。
   - 让 API 路径不强制依赖本地推理模型及 SGLang 的 token 输入；若辅助统计使用 tokenizer，明确它不代表厂商真实分词。

4. **接着解决结果合同**
   - 回答怎样交回 Agent。
   - Verifier 怎样产生评分。
   - 日志、产物、轨迹怎样关联到同一个 Trial。
   - 缺失 token/logprob 时怎样如实记录，不伪造训练数据。

5. **确认无 GPU 的启动方式**
   - Slime 发起路径不能加载训练模型或启动 SGLang。
   - 单独 API 测试通过，不等于完整框架已经跑通。
   - 先验证一个任务，再扩大并发。

6. **第二阶段才接 Agent Sandbox**
   - 理解 Template → Claim → Sandbox → Pod。
   - 完成启动、命令执行、文件传输、结果回收与停止。
   - Agent Sandbox 管编排，底层隔离由 gVisor、Kata 等运行时承担。[官方说明](https://github.com/kubernetes-sigs/agent-sandbox)

7. **K8s 重点学部署和排障**
   - Pod 状态、日志、事件、镜像拉取。
   - CPU/内存请求与限制、OOM。
   - Service、网络访问、Secret、RBAC。
   - 超时、取消和残留资源处理。
   - 暂时不读调度器源码，不自建存储加速系统。

8. **预热是需要验证的优化项**
   - 先测冷启动，再加小规模 WarmPool。
   - 看环境是否匹配、池空时怎样处理、领取后怎样回收。
   - 不预先承诺毫秒启动、千并发、零泄漏。

9. **本地实验的定位要准确**
   - kind 可以帮助验证真实 Kubernetes API、控制器与部署流程。
   - 它适合开发和测试，不能据此证明生产集群的规模、性能与隔离能力。[kind 官方说明](https://kind.sigs.k8s.io/)

10. **现在的行动顺序**
    - 继续整理 issues.md 的四个问题。
    - 优先核对 Harbor 依赖版本、Slime 无 GPU 启动。
    - 再确定 MiniMax 请求和结果适配边界。
    - 小批修改、小批验证；完整 API 任务跑通后，再进入沙箱阶段。

据此记录：先保存并复核上述范围；待实际链路和调用方式稳定后，再评估 SDK 封装，作为学习与交付的后续议题。本轮未确认具体 SDK 接口，也未开始开发或发布。

助手补充的边界判断：

- SDK 是让调用者复用稳定能力的一种交付形式，不等于行业标准；公开接口及其语义、版本和兼容性才是需要明确的合同。
- 已有 Harbor Environment 或 rollout 接口可能已经足以承接当前使用者；优先复用，再根据真实重复调用决定是否增加更高层 Python API，避免包一层同名方法却没有解决新问题。
- 后续需要确定调用者是谁、要完成什么任务、输入输出是什么、错误怎样表达、超时/取消后谁释放资源。SDK 不自动要求另建网关服务。
- 最小封装优先包含配置、一个真实任务调用入口、结构化结果、错误与资源清理约定、一个示例和相应测试；签名从已运行代码提取，不提前臆造 reset/step 等接口。
- 先证明在干净环境中可安装、可调用、可测试，再讨论共享范围、版本管理和发布；不默认必须公开发布到 PyPI。

## 后续完整性复核的问题

十点当前覆盖主线，但不因此宣布已完整实现或足以证明全部岗位能力。进入实施前后，依实际结果复核：

- 谁发起、谁拥有任务和环境、结果返回给谁，是否闭合？
- 成功、失败、取消、资源释放是否有可观察的结果和验证？
- 依赖版本、配置与运行步骤能否让另一环境复现？
- 哪些能力已有框架承担，哪些确实需要新增代码？
- 若最后封装 SDK，它是否让真实调用者更容易使用，而非重复现有接口？

复核产生的新问题进入 [issues.md](../minimax-harbor/backlog/docs/doc-001%20-%20迁移前原文快照.md)，确认后才调整 [plan.md](../minimax-harbor/backlog/docs/doc-002%20-%20总体路线与验收边界.md)。不因本文列出候选能力就预建未读函数卡或宣告掌握。
