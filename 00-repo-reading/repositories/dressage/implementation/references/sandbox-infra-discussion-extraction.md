## 1. 总论：为什么商业沙箱与传统 K8s 被拿来比较

出处：原文 16–17 行。此前十点只保留了范围纠偏，未完整提取总论。

- 原文把两种工作负载对比为：长驻微服务，与瞬时、大批量、需要状态快照的 Agent RL 环境。
- 原文用这个差异解释研究者为什么倾向 E2B、Modal、Daytona，而不是直接使用普通 K8s 集群。

## 2. 瓶颈一：不可信代码与隔离

出处：19–23 行。此前十点提及运行时隔离，但遗漏风险例子与比较链。

- 风险来源：模型生成不可信代码、Reward Hacking、破坏性命令、fork bomb、内网扫描、修改评测脚本。
- 原文对普通容器的描述：与宿主机共享 Linux 内核，内核漏洞或资源竞争可能影响宿主机及同机 GPU 任务。
- 原文把商业沙箱与 Firecracker/gVisor 等技术关联，并声称沙箱内部故障不会波及宿主机。
- 待辨别的关系：隔离实现、资源限制、评测防作弊并非同一个问题；原文将多者合在了这一节。

## 3. 瓶颈二：脉冲并发、冷启动与控制面压力

出处：25–29 行。此前十点提及并发与预热，但未保留完整比较及数字。

- 原文举 GRPO/异步 rollout 的例子：几秒内创建 1,000–10,000 个环境，十几秒后集中销毁。
- 原文把镜像拉取、CNI、挂载等工作计入启动过程，称普通 K8s 冷启动为 5–30 秒，每秒创建数百 Pod 可使控制面失效。
- 商业方案的解释：从内存快照恢复，以 100–300ms 启动、从零迅速扩至数千并发，按秒计费。
- 原文还隐含区分：环境供给速度影响训练等待时间。以上数值均未在材料中附可复核实验条件。

## 4. 瓶颈三：状态快照与分支

出处：31–35 行。此前十点没有作为独立主题提取。

- 场景：MCTS、多步长程任务，从共同中间状态探索不同后续路径。
- 示例：第 5 步完成编译后保存环境状态，再分出 8 条路径尝试修复问题。
- 所需状态：运行中内存与文件系统；原文不只是在说下载文件或预热空环境。
- 原文声称 K8s Pod 无状态、不擅长瞬时克隆，同时将 filesystem/memory snapshot、克隆和“无限分叉”归给多家商业产品。
- 关联例子：将几 GB 的 SWE-Bench 仓库与依赖打包为快照后复用。

## 5. 瓶颈四：镜像规模与存储 I/O

出处：37–41 行。此前十点主要保留“不自建存储”的取舍，未提取机制。

- 原文假定 SWE-Bench/Terminal-Bench 任务具有不同语言版本、依赖和任务镜像，累计数 TB。
- 描述的瓶颈：节点反复拉取、解压大镜像，占用磁盘空间和网络带宽。
- 提出的机制：跨节点共享只读层、写时复制（CoW）、按需加载（lazy loading）。
- 原文声称启动仅加载实际需要的几十 MB、不必先拉完整镜像；需要区分该主张在不同产品/配置下是否成立。

## 6. 商业服务与自建的选择依据

出处：43–51 行。此前十点没有系统提取。

- 商业服务的理由：减少部署维护时间，避免昂贵 GPU 等待环境准备。
- 自建的理由与条件：数据安全、私有化、并发成本、基础设施团队与底层能力。
- 原文列举商业用户群：开源框架、初创公司、研究实验室；提及 Miles、Harbor、Prime Intellect，并给出“95%”比例。
- 原文列举自建公司：字节、阿里、智谱、OpenAI、Anthropic；提出改调度器、接安全运行时、做镜像加速，称之为内部重造平台。
- 讨论留下的选择问题：主要顾虑是安全合规还是成本？任务是代码/命令行，还是桌面/浏览器 GUI？
- 原文给出自托管 E2B/Daytona、轻量 Firecracker 作为进一步讨论的候选，并未实际选定。

## 12. Infra 交付是否只是 SDK：四层模型

出处：129–141 行。此前十点遗漏了完整四层结构。

| 原文层次 | 交付物 | 使用方 | 原文赋予的职责 |
| --- | --- | --- | --- |
| 接口层 | Python 异步 SDK、协议适配器 | 算法工程师、训练框架 | 申请环境、操作文件、得到结果，隐藏 K8s 细节 |
| 控制面 | Gateway/Proxy | SDK 的后端 | 排队限流、连接复用、超时处理、残留资源回收 |
| 环境与数据层 | 镜像工厂、预热池、存储加速 | 任务与评测环境 | 规范化大量环境、加快启动 |
| 可观测与治理 | Trace 管线、监控看板 | 算法复盘与运行排障 | 轨迹、token、reward、GPU 等待、创建耗时、OOM |

原文结论是“SDK 是交付界面之一，运行服务与环境支撑也属于交付”，不应提取成“最后只需要一个 SDK”。

## 13. 为什么提出轻 SDK 与重服务端

出处：144–152 行。此前十点保留了 SDK 可后置，但遗漏主要论证。

- 原文担忧客户端直接连接 K8s 时，512/1024 并发及 1,000 个 Watch/Exec 连接导致控制面压力。
- 另一担忧是客户端进程异常退出、Ctrl+C 后清理未执行，资源残留。
- 所提架构：SDK 只做异步 HTTP/gRPC 和协议适配；后端 Sandbox Manager/Gateway 管理生命周期。
- 后端示例：FastAPI/Go 服务、心跳检测、超过 5 分钟回收、预热池水位调节、Trace 异步落盘。
- 原文把 reset/step/evaluate 与 Harbor/Gym 统称为可直接对接接口；提取保留此说法，但不能视为这些框架接口完全相同。
