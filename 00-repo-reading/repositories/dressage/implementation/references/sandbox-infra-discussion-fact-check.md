# 沙箱基础设施 discussion：事实核对

核对日期：2026-11-17。对象：[原文](sandbox-infra-discussion-original.md)与[17 项提取稿](sandbox-infra-discussion-extraction.md)。

## 结论

**不是全部成立。问题意识多数合理，但原文混合了真实能力、条件性工程判断、未经支持的数字和过度确定的岗位推断。不能将整篇作为事实依据。**

本稿只核对讨论，不新增实施任务。产品文档随版本变化；以下“当前文档有此能力”不代表历史版本、本地安装版本也有，更不代表已实际跑通。官方产品宣传的性能也不是本项目实测。

## 对照原来的 17 项

| 提取项 | 判断 | 应当保留或修正的理解 |
| --- | --- | --- |
| 1. 工作负载与平台选择 | 部分成立 | Agent/RL 可能有突发并发、隔离和状态需求；并非所有任务都需要 MicroVM、快照或瞬时销毁。K8s 与商业沙箱不是同一层的互斥选项，沙箱服务也可建立在 K8s 上。[S1][S8] |
| 2. 隔离 | 风险真实，表述过度 | 普通容器共享宿主内核，存在逃逸和资源干扰风险，但“会逃逸”“必然导致宿主宕机”不成立。gVisor 是用户态应用内核，并非每个沙箱有一套独立 Linux 客体内核。任何运行时都不能保证绝不影响宿主。隔离、资源限制、保护评分脚本是不同控制。[S2] |
| 3. 并发与冷启动 | 机制成立，数字无通用依据 | 冷启动可能包含镜像、网络、存储和进程准备；创建压力可能影响控制面。没有证据证明“数百 Pod/s 必挂”或“1000 个连接必瘫痪”。1000–10000 环境、5–30 秒、100–300ms 都不能无条件推广。[S3] |
| 4. 快照与分叉 | 能力存在，适用性有条件 | 状态分叉适用于部分搜索/恢复任务，并非 Agent RL 普遍刚需。Pod 可承载有状态程序，“Pod 无状态”错误；但 Pod API 本身不等于完整进程快照/分叉 API。商业产品能力也随运行时和快照类型不同。[S4][S5][S6] |
| 5. 镜像与 I/O | 基本成立，归属错误 | 大镜像与重复拉取可能是瓶颈；分层复用、CoW、懒加载是有效机制，不是商业沙箱独占。K8s 的 containerd 生态也有懒加载实现。不是所有 benchmark 每题都有完全独立镜像，也不能断言每次只读几十 MB。[S7] |
| 6. 商业与自建选择 | 判断维度合理，市场断言无证据 | 成本、合规、交付速度、运维能力是合理维度。“95%”“只有头部大厂自建”“自建必须重写调度器”没有得到证明，应撤回。文中公司名单不能当作已核实的内部架构。[S1][S8] |
| 7. Agent Sandbox 能力 | 核心能力成立 | 官方项目有 Sandbox、Template、Claim、WarmPool；当前 Python 文档确有 AsyncSandboxClient 和 files API。运行时隔离仍依赖节点配置，SDK 文件操作也依赖服务端，不是装一个包即可使用。[S1][S9] |
| 8. 使用不多的原因 | 日期错误，其余主要是推测 | 官方已在 **2025-11-11** 宣布项目，不是 2026 年初。“使用不多”本身没有采用率数据，不能先当事实再解释原因。运维前置成本真实，但“两周”“K8s 1.29+”“均需嵌套虚拟化”不是通用要求。[S10][S11] |
| 9. JD 映射 | 有相关性，不足以确定职责 | 所给 JD 确实要求 Agent 框架、并发、评估和 K8s 经验。不能由此推断腾讯必然要自建私有 E2B、使用 Agent Sandbox，或该岗位负责内核/调度器/整套沙箱平台。它也没有将工作限于环境工程。依据是用户给出的 JD，而非已核实的团队内部需求。 |
| 10. 本地模拟 | 可用于学习，不能等同生产 | kind 可运行本地 K8s，适合接口、资源生命周期与故障行为实验。“零成本、10 分钟、100% 复刻生产”不成立：机器、网络、存储、云权限、规模和故障域均不同；API 可能收费。200 行/20 并发/池 5 个只是示例。[S11][S12] |
| 11. 检索线索 | 不能作为已核实证据 | 原帖的知乎/CSDN 标题、摘要和日期缺少可核对的原文链接，不足以支持吞吐、采用率或技术结论。没有据此确认 DSec 的具体设计；它保持待核实，不纳入事实链。 |
| 12. 四层交付 | 合理的分析框架，不是标准 | SDK、生命周期服务、环境供给、可观测性可以帮助划分职责，但不存在由本文证明的“固定四层行业标准”。组件可能已由平台提供，不能推成每个岗位都要各写一套。 |
| 13. 轻 SDK、重服务端 | 合理选项，不是必选 | 服务端管理生命周期有助于在客户端消失后回收资源；但已有 controller/router 可以承担部分职责，不能从并发数字直接推出必须新增自研 Gateway。5 分钟心跳是策略示例；需考虑误回收。Harbor 环境接口与 Gym reset/step 不能混作同一协议。[S1][S3] |
| 14. 交付展示 | 方向合理，性能承诺不成立 | 可安装包、复现用例、发布流程和监控可作为证据，但并非全部必交。50 行接入不证明已完成 GRPO/PPO 训练；P99<300ms、1000 并发、零泄漏需要定义测试条件、观测窗口并实测，不能直接写成 SLA。 |
| 15. 大厂分工 | 可用作示意，不能当组织事实 | 底层基础设施与上层 Agent 框架的职责区分合理；具体公司采用哪些团队、语言、人数、是否由本岗位承担，原文没有证据。 |
| 16. 中型团队 | 可能存在，不具普遍性 | 小团队可能复用平台并由少数人覆盖更多职责，但“50–500 人公司必然没有底层团队、该岗必须全包”不能由规模推出。 |
| 17. 招聘与 GPU 效率 | 条件性因果成立，概括过度 | 当环境供给/执行成为流水线瓶颈时，可能让推理或训练设备等待；异步缓冲与资源配比会影响程度。不能断言所有 GPU 等待都由沙箱造成，也不能说某年后预训练被 RL 取代。“算法研究员写不好工程”“JD 100% 对应整套沙箱建设”应删除。 |

## 最需要修正的几个具体关系

### K8s、运行时和沙箱服务不是三选一

K8s 负责资源对象与编排；gVisor/Kata/其他运行时提供不同隔离边界；Agent Sandbox 提供沙箱资源与生命周期能力；商业平台还可能提供托管、计费和运维。应按层比较，不能用“商业服务能预热，所以 K8s 不适合”作结论。[S1][S2][S8]

### 预热不是不需要准备镜像，也不是无限容量

WarmPool 提前创建可领取实例，将部分准备工作移到请求到来前。命中可降低等待，但补池、首次拉取、依赖准备和计算资源仍有成本；池耗尽后的表现需要单独衡量。Claim 及协调仍可能涉及控制面，因此“有池就无控制面压力”和“有池也必然打挂”都不成立。[S1][S11]

### 快照要分清文件和运行中状态

文件快照不必然保存进程内存、连接或外部服务状态。当前 Modal 文档把文件、目录、内存快照分开，内存快照标为 Alpha，并列出连接、进程、GPU 和实例类型限制。Daytona 也按 sandbox 类别区分 memory snapshot 与 fork 能力。因此不能写成几家产品都支持任意状态的无限分叉。[S5][S6]

### Agent Substrate 确实存在，但原帖解释过简

Google 的 2026-09-15 公告明确介绍在 GKE 上运行 Agent Substrate。它不是“完全绕开 K8s 的另一个平台”，也不能简单等同于 Agent Sandbox 的默认控制面。公告中的密度和恢复速度属于供应方给出的能力描述，不证明所有部署都有同样性能。[S8]

### 安全运行时与硬件虚拟化不能混说

gVisor 的用户态内核机制不等于 Kata 的虚拟机方案；不能把“嵌套虚拟化”写成两者的统一前置。是否需要嵌套取决于所选运行时及宿主是否本身为虚拟机。官方 Agent Sandbox quickstart 还提供不带强化隔离的基本 kind 路径，用于功能学习；这不代表它足以运行任意敌意代码。[S2][S11]

### SDK 可以是交付物，但不是岗位要求的最终标准

从给定 JD 能确定的是：可复用组件、策略与评测接入、稳定性、性能、实验需求迭代，以及 K8s/容器实践。SDK 是暴露这些能力的一种形式，不是这份 JD 承诺或要求的唯一形式。是否需要独立 SDK、网关或镜像流水线，应由真实调用方与现有平台边界决定；本次核对不替用户新增这些建设任务。

## 原文数字如何处理

| 原文数字/断言 | 核对处理 |
| --- | --- |
| 95% 的框架/实验室采用商业平台 | 没有统计来源，撤回 |
| 几百 Pod/s、1000 连接必打挂 | 无通用阈值，撤回；保留“可能形成压力” |
| 普遍 5–30 秒 vs 100–300ms | 不可跨产品/机器/冷热状态直接比较 |
| 瞬时 1000–10000 环境、十几秒任务 | 可以是负载示例，不能当所有 RL 的特征 |
| 只有头部大厂自建、必须改调度器 | 无依据的排他性结论，撤回 |
| 2026 年初发布 Agent Sandbox | 改为至少 2025-11-11 已正式公开宣布 |
| 1.29+/1.30+、两周、10 分钟 | 不是已经核实的统一前置/工期，按选定版本与机器验证 |
| 200 行引擎、50 行训练接入 | 示意工作量，不是验收结果或复杂度保证 |
| P99<300ms、1000 并发、泄漏率 0 | 未实测目标；必须定义统计口径与负载，不能宣称已具备 |
| 一年数百万美元、数千 GPU、团队几十上百人 | 原文组织/成本示例，不能套到腾讯岗位 |
