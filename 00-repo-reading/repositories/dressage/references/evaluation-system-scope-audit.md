# 三个 topic 是否足以支撑 Dressage × Harbor × Agent Sandbox 评测体系

[主题与范围规划](topics-and-step-scopes-after-step006.md) · [兼容性核对](agent-sandbox-harbor-compatibility.md) · [项目入口](../README.md)

2026-11-08。用户明确本次问的是评测体系能否由三个 topic 的内容实现，不是再审查岗位覆盖。本文据此单独评估，不替换岗位目标，也不把规划和实际实现混为一谈。

## 1. 先限定这里的“评测体系”

以现有项目为基础，首版能够配置一组任务、选择 Agent 与模型、在 K8s 沙箱执行、调用 Verifier、保存逐次结果并汇总、处理有限重试/取消并回收资源。配置、代码/模型版本和产物可关联，便于复跑与比较。

不把网页管理台、多租户计费、任意跨集群调度、全部 Agent、训练集群或全量灾备恢复当作这次首版的隐含条件。

**结论：三个 topic 的职责划分足够，当前 scope 的交付标准还不完整。补齐几处实现与验收后，可以作为首版评测体系的实施路线；只读完现有函数不会自动得到该体系。**

## 2. 三个 topic 在成品中的作用不同

| topic | 对评测体系的作用 |
| --- | --- |
| 原生 Dressage 单任务闭环 | 建立已读背景，理解环境、模型调用、结果、轨迹和清理；原生 Paddock/BlackboxServer 路线不再作为每个 Harbor Trial 必经的一层 |
| Dressage × Harbor 接入与验证 | 组织任务与尝试、复用 Agent/Verifier、接模型与采集、保存结果，并完成整合 |
| Kubernetes 沙箱资源治理 | 提供实际环境生命周期、预热领取、访问与回收能力，通过 Environment 适配被 Harbor 使用 |

运行时核心是 Harbor Job/Trial 使用 Agent Sandbox 环境；Dressage 插件在生命周期中接入模型路由和结果/轨迹。三个学习主题不需要全部串成同一条调用栈。

## 3. 当前哪些内容已经有安排，哪些还未闭合

| 评测环节 | 已有范围 | 尚需落实的交付标准 |
| --- | --- | --- |
| 任务、Agent、Verifier | Step 010–012 | 选定一种 Task 格式和两种代表 Agent，明确如何配置与替换；已有 Harbor 实现优先复用 |
| K8s 环境 | Step 013 + K8s topic | 不能停在接口映射表；要取得或实现能导入的 Environment，并验证创建、执行、文件/目录和删除 |
| 版本与依赖 | Step 013 前提与兼容性 reference | 决定并锁定可运行版本组合；当前示例适配目录缺失，且 >=0.25 与 Dressage 0.18.0 冲突，属于明确阻碍 |
| 模型请求及 Dressage 采集 | Step 014 | 选择实际后端，验证完整请求与控制接口。若使用商业 API，不能只改 URL 或只关 require_trainable_tokens |
| 评测结果与汇总 | Step 015 | 除产物保存和 Sample 转换，还要规定最终尝试选择、评分/执行错误分类、汇总分母及报告输出 |
| 失败与资源治理 | Step 016 | 说明重试条件、次数、超时和取消的结果归属，验证不会重计一次任务或遗留不可追踪环境 |
| 可部署与可复跑 | Step 017 | 固定一套启动方式、镜像/资源配置、RBAC、网络入口和产物位置；用任务集与失败案例实际跑通 |

这里不缺第四个主题，缺的是把若干步骤从“能说明”补成“有实现、有验收”。

## 4. 应如何补实既有 scope

### Step 013：交付一个实际可用的环境适配

1. 先固定 Harbor/Dressage 版本，并取得缺失实现或明确需要补齐的模块。
2. 选择执行通道：普通任务镜像可使用 pods/exec 与 tar；若使用 SDK 的 HTTP/gRPC，必须确保对应服务和运行约束真实存在。
3. 兑现 start/stop、exec、文件和目录传输，以及 cwd/env/user/timeout/退出状态合同。
4. 保存一套最小集群配置和一题冷创建证据。WarmPool/Claim 的热路径可在冷路径通过后增加。

### Step 014：交付实际可用的模型与采集链

1. 在原生支持的 SGLang 路线与需要适配的商业 API 路线之间作明确选择。
2. 验证 Pod 到 Gateway、Gateway 到 Proxy/后端的可达性和身份传递。
3. 验证模型请求、会话收尾、轨迹读取三类合同；保留真实数据与缺失项。
4. 先跑通 Harbor 原生结果可作为局部验证，但不能据此声称 Dressage 采集已经接好。

### Step 015：交付评测结果格式与汇总规则

1. 一次结果至少关联任务、Agent/模型、配置版本、run/trial/attempt/session、环境资源、状态、分数、耗时和产物位置。
2. 区分正常完成但低分、Agent 执行失败、环境/模型基础设施失败、Verifier 失败、取消和超时。
3. 明确同一任务的多个 attempt 哪一个进入最终报告，以及汇总时怎样避免重复计算。优先核对和复用 Harbor 的已有汇总，而非重新实现一套计分器。
4. 输出逐题结果和批次摘要，用于比较两种 Agent/模型或两次配置。评测首版不要求启动 Slime 训练；Sample 转换保留为之后训练消费的接口。

### Step 016/017：交付一套有限但完整的验收

1. 一题 Oracle/确定性执行通过环境与 Verifier 路径。
2. 一组固定任务使用真实 Agent 和实际后端，生成完整结果与摘要；更换另一种代表 Agent 后仍使用同一套任务/环境合同。
3. 正常低分与基础设施错误在报告中可以区分；重试不会重复计分。
4. 少量并发的 Claim/环境独立；热领取确实命中预先就绪的环境，未命中能正确冷创建。
5. 一次超时或外部取消后，任务状态、路由、轨迹及环境清理均有可追踪的结论。
6. 同一配置可以再次启动评测并保留独立 run 标识。这里的可复跑不等于逐 token 确定性，也不等于跨进程断点续跑。

当前 Dressage 插件 on_job_start 明确拒绝 is_resuming 的 Job。首版可以约定失败后新开一次运行并保留旧产物；若要求进程崩溃后原位恢复，则还需要单独设计与实现，不能由“有重试”推导为“有完整恢复”。

## 5. 本次建议的状态

这次完成的是评测体系完整性审查。现有三个 topic 和已创建 scope 不删除、不重新编号；上述交付标准尚未批量回填正式 scope，也没有开始实现。当前直接阻碍仍以版本和适配代码核对为准，不能写成已经解决。
