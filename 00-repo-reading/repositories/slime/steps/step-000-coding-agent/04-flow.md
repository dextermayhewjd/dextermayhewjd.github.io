## 2026-10-23：核心骨架如何处理新增的执行追踪

用户继续追问：

> 但是这里我觉得多了一些类似于这里trace_span的部分吧？
> 是否需要考虑一下呢还是你觉得这里干活的核心股价保留这些就可以了？

**助手核对与取舍**：

- `trace_span` 包住业务阶段，记录开始、结束、父子层级及附加结果；例如 `agent_run` 内部仍由 `harness.run` 启动 CLI 并等待，之后通过 `span.set` 记录退出码。
- Step 0 需要交代这层职责，让读者能从裁剪后的骨架对应回真实源码；重复的追踪包装可以折叠。已在 [scope](01-scope.md#trace-span-boundary) 增加简短说明与可展开的代码对照，原业务骨架保留。
- 按数据用途决定详略。`collect_metrics` 的 `compact_limit_reached` 会影响样本是否标记为截断，不能仅因它看起来像统计就折叠掉。

**证据与边界**：静态核对 `18868a79` 的 `generate.py:286–307、340–348` 与 `trace_utils.py::trace_span`；没有运行远端任务或验证真实追踪输出。本轮继续停在 Step 0，不展开追踪机制的独立函数卡片，不将助手解释记为用户已经理解。
