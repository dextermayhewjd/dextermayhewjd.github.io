# generate() 生命周期的阅读结论

记录日期：2026-10-22。

本文保存这次关于“是否还需要把 `generate()` 的核心调用补齐”的讨论结论。它补充 [Slime 后续阅读顺序](README.md) 与 [Slime → Dressage 阅读顺序](slime-to-dressage-reading-order.md)，保留原有两份记录，不另建一套阅读进度。

## 1. 这次解决的问题

用户提出：

> 那么不需要考虑原来的 generate 全部读完吗？这里不需要看 adapter.open_session，还有 boot_agent_sandbox，还有 swe.prepare_workspace，或者这里的 swe.git_diff 了吗？

此前的时间安排把这部分概括为“回顾主线”，没有充分区分已经读过的局部实现与尚需展开的核心调用。这些内容仍需要安排阅读，不能仅凭已经有 Step 001–003，就视为整个单题生命周期已经理解。

## 2. 确认的判断

**需要读清楚 `adapter.open_session`、`boot_agent_sandbox`、`swe.prepare_workspace` 和 `swe.git_diff`。它们属于 `generate()` 的核心生命周期。**

本轮应该完整走通 `generate()` 的正常执行链，并补上关键失败与清理分支。每个主要调用读到能够说明以下关系：

- 为什么执行到这里，接到什么输入。
- 实际完成什么工作，改变了哪些状态或资源。
- 返回什么，或者留下什么副作用。
- 下一步由谁接手；失败或退出时由谁收尾。

阅读深度以这些交接能够连贯解释为准。暂时折叠的配置、日志、辅助实现和分支，只有阻碍当前问题时再展开。首轮下钻沿用阅读指南：控制在两层以内，弄清输入输出后返回主线。

原先“先吃透一条 Agent 执行与评测链路，再看 Dressage 怎样组织这些能力”的判断继续成立。这里明确了这条链路需要覆盖哪些内容；学习目标仍然是对齐腾讯混元 Agent 强化学习框架岗位，不要求通读整个 Slime。

## 3. 时间顺序：把原第 05 项展开

下表的 **05.1–05.7 是此前阅读时间表第 05 项的细分编号**，不是新的 Step 005，也不表示已经创建步骤、完成阅读或掌握这些函数。

先接续当前已确认的阅读问题，再按下面的顺序补齐单题生命周期。已有函数记录用于提醒与复用，实际缺口仍需阅读。

| 时间序号 | 阅读入口 | 必须补清的关系 | 如何利用已有 steps |
|---|---|---|---|
| **05.1** | `adapter.open_session` | 会话在哪里登记？保存什么配置？后续 `_run_turn` 怎样使用这个会话？ | 接回 Step 001 的请求处理，以及 Step 003 的关闭与导出 |
| **05.2** | `boot_agent_sandbox` | Agent 的运行环境怎样准备好？交出的 `sb` 是什么？退出时谁回收？ | 复用 Step 002 的 Sandbox 基础，但仍要读这层组织逻辑 |
| **05.3** | `swe.prepare_workspace` | 工作区和题目怎样准备？为什么返回 `baseline`？它留给谁使用？ | 补齐 Agent 开始工作前的条件 |
| **05.4** | `harness.run` | 怎样使用准备好的工作区、会话和 Adapter 地址启动 Agent？结束后留下什么？ | 复用 Step 001；尚未读清的启动与等待关系继续补 |
| **05.5** | `swe.git_diff` | 怎样根据初始基线取得 Agent 的修改？返回的补丁交给谁？ | 接到 Step 002 的 `_apply_diff` 和评测输入 |
| **05.6** | `run_evaluation` → `finish_session` | 补丁怎样得到奖励？奖励与轨迹怎样组成最终样本？ | 复用 Step 002、003，重点检查交接是否连贯 |
| **05.7** | `generate` 中的异常、超时与清理 | 中途失败时返回什么？会话和沙箱分别由谁收尾？ | 补齐整次任务的生命周期 |

这是阅读顺序。05.7 的异常与清理可能发生在执行过程中的多个位置，不能把它理解成程序只在全部正常步骤结束后才处理失败。

## 4. 两条必须补齐的关系

### 会话从哪里来，最后怎样结束

```text
open_session
    → 会话中的请求处理：_run_turn
    → 会话结束与样本导出：finish_session
```

- `open_session` 解释会话状态和配置从哪里来。
- `_run_turn` 解释一次请求怎样使用这些条件，生成回复并记录轨迹。
- `finish_session` 解释会话怎样收尾、取出轨迹并交付结果。
- 只读请求处理和结束阶段，会缺少会话的建立与使用之间的联系。

### 评测用的补丁从哪里来

```text
prepare_workspace
    → Agent 在工作区修改代码
    → git_diff
    → run_evaluation
```

- `prepare_workspace` 交代开始工作的条件与初始基线。
- `harness.run` 启动并等待 Agent 在这个工作区执行任务。
- `git_diff` 把工作区改动提取为可以交接的补丁。
- `run_evaluation` 接收补丁并评估。
- 只读评测内部，会缺少“被评测的改动如何产生、如何提取”的关系。

## 5. 已有阅读可以复用到什么程度

- **Step 000 的核心骨架**提供全局定位；骨架中出现过一个调用，不代表已经理解它的内部组织。
- **Step 001 的 Adapter 与 `_run_turn`**提供模型请求、协议处理和轨迹记录的基础；还要核对它们怎样使用前面建立的会话，以及 Harness 怎样启动并等待 CLI。
- **Step 002 的 Sandbox 与评测**提供环境操作和补丁评估的基础；仍需补齐 Agent 侧环境准备、初始工作区和补丁提取。
- **Step 003 的关闭、轨迹和样本**提供任务末端的认识；仍需把这些结果接回 `generate()` 的输入、执行过程和返回值。

特别需要区分：

> 读过 `E2BSandbox.__aenter__`，不能直接视为读过 `boot_agent_sandbox`。前者解释具体 Sandbox 实现的进入能力；后者解释如何组织出可供 Agent 使用的运行环境。

这些区别只用于决定回顾深度。已有记录继续复用，尚未读清的组织逻辑继续补齐，不因需要提醒而清零原有进度。

## 6. 放在后续路线的什么位置

这些生命周期内容应当在后续系统阅读批量运行、观测与 Dressage 之前补齐。

当前可以有一个局部调整：**如果 `sid` 和会话配置的来源正在阻碍 Step 003，就先短读 `open_session`，然后回到 Step 003。** 这是为当前问题补最小前置，不要求立刻把整个生命周期全部展开。

完成当前问题后，再沿 05.1–05.7 检查和补齐主线。对已经读清的内容只做职责与交接回顾；其余内容实际展开时再确定步骤和函数卡片。

完成这一段的标准是：能够连贯说明“一道题怎样获得环境与会话、启动 Agent、留下改动、得到评测、导出样本并释放资源”，并指出关键交接对应的源码入口。随后进入已保存的批量运行、观测、训练接口和 Dressage 安排。
