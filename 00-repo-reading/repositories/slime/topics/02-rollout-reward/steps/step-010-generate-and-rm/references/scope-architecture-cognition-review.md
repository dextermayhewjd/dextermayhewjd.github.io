# 对完整 scope 的架构与认知评估

[完整 A/B 候选](scope-stage-navigation-proposal.md) · [正式 scope](../01-scope.md)

2026-10-26，用户要求结合资深架构师的考虑方式与认知科学评估。以下为助手依据源码、实际阅读问题和研究作出的建议，不是“研究已经验证本学习者适合某版”的结论。正式 scope 尚未替换，不处理 Hugo。

## 1. 判断：保留主体，以 A 为基础区别对待不同分支

四段主线继续保留：共享状态 → 受控生成 → 结果处理 → 评分交付。精简目标是降低同时需要处理的新关系数量，不是单纯减少行数或函数名。

原 A 把 evaluation 参数支持检查与 abort_mode 分派都显式写成 if/else。我的进一步建议是：前者可以用紧邻调用的接口说明表达，后者保留可见分支。这是对 A 的局部微调建议，不新增整套路线，也未自动采用。

## 2. 架构上先判断代码承担的责任

| 需要保留的关系 | 当前例子 | 建议呈现 |
| --- | --- | --- |
| 对象身份与数据归属 | state、输入 Sample、返回 Sample 列表、queue_input | 保留真实名称与关键赋值 |
| 控制及资源范围 | semaphore 取得/归还、DP with 嵌套、aborted 返回 | 直接保留结构，不能只留一句“受控生成” |

这里收起的是“如何检查函数签名”，不是说 evaluation 的值没有业务意义。当前模式是 evaluation=False；当问题变成评估模式如何改变行为时，evaluation 本身就是主要阅读对象。

## 3. 认知科学给出的约束

### 3.1 组块要靠已有关系，不能靠标题命名

Cowan 对 chunk 的界定依赖概念之间已有的联系，而不只是信息被排成一组。把多个控制操作命名为“受控生成”，不能据此假定学习者已经将它们当作一个熟悉单位。[Cowan，2001，第 1.3 节](https://memory.psych.missouri.edu/assets/doc/articles/2001/cowan-bbs-2001.pdf)

应用到本例的判断：保留四段整体位置，同时仍显示 semaphore、pacer、DP 上下文这些正在建立关系的节点。四段来自职责分解，不是把某个工作记忆容量数字套成“最多四个函数”。

### 3.2 同时需要理解的材料应就近，冗余细节可以收起

Chandler 的研究讨论了需要来回整合的信息来源以及冗余信息带来的额外负担，包含技术和计算机材料的实验。[Chandler，1993](https://www.aare.edu.au/data/publications/1993/chanp93034.pdf)

应用到本例的判断：当前读 _run_server_abort_generate 时，应在同一个阅读位置看到 generate_call 从哪里来、活跃计数加减和返回到哪里；不要求在五份文件间拼接这个最小关系。但也不需要把整个上游生成器、所有参数和完整 abort 服务流程一并展开。

### 3.3 细节应该随理解发展调整

认知负荷研究综述将复杂任务、先前知识和学习者的发展水平一起考虑，而不是为所有学习者固定一种展示密度。[van Merriënboer 与 Sweller，2005，作者摘要记录](https://eric.ed.gov/?id=EJ732431)

应用到本例的判断：已明确的关系可以缩成提示，需要回忆时仍能原位展开；新问题只打开相关节点。某个函数曾读过，不等于可以永久省略它的职责提醒。

## 4. 对当前阅读记录的具体建议

1. **主 scope 稳定保留完整四段。** 当前阅读位置变化不导致整体地图来回重排。
2. **当前一段展开必要真实调用。** 本轮是 generate_call → 服务端等待包装 → 返回父函数，突出这一条交接。
3. **分支区别看待。** 保留 request/server 的路径选择，evaluation 签名检查先用短注保留存在与用途。
4. **对象卡、方法卡和 scope 各守职责。** 对象卡定位字段；方法卡说明这次操作与输入输出；scope 负责顺序、范围、分支和返回位置。方法卡仍包含最小调用语境，不能要求每次拼接全部上游。
5. **按实际反馈调整。** 判断表达是否合适，看能否辨认当前对象、指出下一次交接、解释移除某个清理会影响哪项状态；不以页面变短、建卡完成或构建通过代替理解。

当前对话里的问题集中在 pending 与 scheduled、生成器暂停与退出，以及多个计数的作用范围。因而我会优先让对象身份与执行时机可见，再精简熟悉的接口语法。这是基于当前问题的设计推断，不是对学习能力的诊断。

## 5. 尚未验证什么

研究支持的是一般设计原则，没有直接比较这份 Slime scope 的 A/B 学习效果。当前建议仍需实际阅读反馈验证；不声称代码块越短越好，也不声称更完整的源码必然更难理解。
