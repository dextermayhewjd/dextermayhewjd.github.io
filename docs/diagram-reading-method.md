# 用架构图拆解核心机制：阅读笔记的一种格式

这套方法来自 Learn Claude Code 系列中已经采用的图 1／图 2 对照。后续读项目、学课程或开发新机制时，可以选择它作为笔记格式，不要求所有笔记采用同一套图。

目标是让读者在当前页回答三个问题：这个机制在哪里、改变了什么、内部如何工作。图用来定位关系；代码、例子和验证用来核实行为。

## 1. 先选择这篇笔记要解释什么

| 阅读目标 | 推荐图组 | 适用例子 |
|---|---|---|
| 理解系统如何演化 | 图 1：上一轮系统；图 2：本轮系统；复杂时加图 3：本轮核心 | 在原循环中加入 Task、Compact 或 Goal |
| 单独吃透一个机制 | 图 1：机制在宿主中的位置；图 2：机制内部流程 | 阅读缓存、调度器、技能装载或事务提交 |
| 建立最初的系统模型 | 一张基础图，按需加局部图 | 第一章、从零阅读一个项目 |

两种双图模式不能混称：演化对照的图 1 是实际旧系统；独立机制的图 1 是当前宿主定位图。开头注明采用哪种模式，再说明每张图的任务。

若两张图已能说明位置、输入、判断、输出与返回，就不必补第三张。机制跨越多个生命周期时，可以再拆专题图；整体图仍保留它接入系统的接口。

## 2. 演化对照：旧系统 → 本轮系统 → 核心机制

### 图 1：认出上一次看到的系统

复用上一章的默认整体图，保留节点、布局与连线。这里的“复用”是结构复用，颜色重新按本轮变化标注：

- 蓝色：原有且保留。
- 橙色：本轮将改造的旧位置；框内仍是旧实现。
- 灰色虚线框：内部细节将在图 2 合并，功能仍保留。
- 红色虚线框：原有对象将在本轮真实移出，仍作为旧流程对照。

不要提前添加本章的新模块，也不要补画上一章没有显式画出的旧步骤。读者在图 1 上只需认出旧系统，并找到下一张要处理的位置。

复用上一章默认图，不复用读者临时点击展开的状态，也不沿用上一章的紫色“新增”标记。

### 图 2：看清新机制接入哪里

尽量在原骨架上修改。保留主流程与已有模块的身份，必要时调整间距、局部位置和画布尺寸，并说明对应关系。

本轮机制应连进完整系统，至少标明：

1. 谁触发它，触发在主流程哪一环。
2. 输入从哪里来，读取或修改哪些状态。
3. 有哪些影响控制流的判断、拒绝或等待分支。
4. 结果交给谁，怎样继续、返回或结束。

把新机制放在图下方却不连到原循环，不能说明它的接入位置。只展示工具名称也不足以说明 handler、内部逻辑和结果回传。

### 图 3：复杂时，单独展开本轮核心

图 3 解释图 2 中新机制的内部过程，不再复制完整宿主。保留必要输入、内部判断、状态变化、输出与返回边界。

每个关键步骤下面配相应函数和解释；最后用伪代码接回主循环。可复用网站的函数阅读器与悬停追踪，但静态图和正文也应能独立读懂。

## 3. 独立机制：宿主定位 → 局部工作过程

没有上一轮版本时，不虚构一个“改造前”系统。

**图 1 是定位图。** 画出已有宿主的必要骨架，标出目标机制的入口、状态关系和输出。已知环境用蓝色；紫色表示本篇关注的机制，不表示历史上刚新增。明确使用机制视角图例。

**图 2 是局部图。** 只展开目标机制，将输入、检查、处理、状态读写和输出串起来。函数、文件位置和源码版本在正文中逐步对应；循环或重试放在直线主流程下方。

例如研究一个缓存：定位图说明调用者在请求前查缓存，命中返回给谁；局部图说明 key、命中条件、未命中计算和写回。两张图都描述当前实现，不需要编造旧版本。

## 4. 颜色、线型与抽象层次

| 标记 | 演化对照模式 | 独立机制模式 |
|---|---|---|
| 蓝色 | 原有且保留 | 已有宿主或执行环境 |
| 橙色 | 旧对象被修改／职责迁移；图 1 显示将改造的位置 | 有实际改动时才使用，否则不用 |
| 紫色 | 本轮真正新增 | 本篇核心机制，图例明确注明视角 |
| 红色虚线／删除线 | 对象真实移除或替换 | 通常不用；只有真实移除对照才使用 |
| 灰色实线框 | 存储或辅助节点 | 存储或辅助节点 |
| 灰色虚线框 | 细节合并，功能保留 | 合并展示的已有内部细节 |
| 灰色来源标签 | 原有细节本轮首次展开 | 实现出处、所属文件或补充说明 |

**第一次画出来，不等于第一次存在。** 一个早就存在的用户输入或工具实现，本轮才展开时仍按真实行为着色，并加来源标签；不能因首次出现就涂紫色。

颜色之外也使用名称、说明和线型。每张图旁保留完整图例，可折叠但应看到已使用的色块；改图时同步核对图例文字、颜色和线型。

实线箭头表达流程或数据方向，虚线表达引用、注册或关联，具体含义用文字注明。不要把所有箭头都解释成一次顺序执行。

## 5. 图变大时，只折叠内部细节

先增加必要空间、整理连线路径，再判断是否需要合并已讲过的细节。没有固定的“最多几个框”，也不要求每章永久保留每个函数。

折叠后仍要保留：调用者、触发位置、输入、结果去向、控制影响、实现来源。已学模块可以缩成带职责摘要和章节链接的接口；本轮重点仍应展开。

模块按实际职责归属。工具定义、工具执行、请求前处理、状态存储和退出检查不是同一层；不能因为想压缩总图，就把 Skills、Compact、Memory 或 Goal 都塞进工具实现框。

主循环、关键门控、后台交付、状态读写接口等影响心智模型的部分，不应在合并时悄悄消失。连线不得穿过节点，不共享难以区分的线段；回线放在主线下方，窄屏在图内滚动。

## 6. 从图逐步读到代码

每个机制段落采用这个顺序：

1. 说明这一步解决什么问题。
2. 标明所属层：宿主入口、模型工具定义、分发、内部机制或存储。
3. 给出必要源码，说明输入、输出、状态变化和分支。
4. 指回图中的步骤与下一步。

读完局部函数后，用一段主流程伪代码解释接入位置。不要把整份代码堆在一起再写一段总结，也不要只展示空函数名。

注明仓库、版本、文件路径和函数名；自己的简化示意明确标为伪代码。区分实际集成、独立教学脚本与累积学习架构；图中保留旧能力索引，不等于当前源码已注册这些能力。

## 7. 在这个博客里复用

草稿模板位于 [archetypes/mechanism-note.md](../archetypes/mechanism-note.md)，可以生成项目或课程笔记：

```bash
hugo new content --kind mechanism-note projects/my-project/01-mechanism/index.md
```

草稿提供问题、两图模式、可选图 3、分段代码、接回流程与验证栏。它不会生成虚假的完成图或启用交互；作者需要填入实际来源、代码与图形，删除未使用的模式后再发布。

这个命令创建叶子页面包；把 SVG 放在同目录的 `images/` 中，便于现有插图组件读取页面资源。章节总览继续沿用 `_index.md`。实际插图和上一章资源引用，参考 [写作规则中的文件与复用方式](learn-claude-code-writing-rules.md#7-文件与复用方式)。演化图用 `legend="evolution"`，独立机制图用默认机制图例。

图的变化规则沿用本文；Learn Claude Code 的具体章节决定与网站交互细节继续维护在 [现有写作规则](learn-claude-code-writing-rules.md) 中。

## 8. 发布前，读者能否解释这些问题

- 这篇采用演化对照，还是独立机制拆解？
- 图 1 是否忠实保留了它声称回顾的系统？
- 图 2 能否说明机制在整体流程中的入口与返回？
- 哪些是新增、修改、真实移除或只是首次展开？
- 合并后的模块是否仍有明确接口和来源链接？
- 图、函数、伪代码是否描述同一实现与版本？
- 哪些结果已验证，哪些仍只是推断或未验证？

构建和交互检查证明页面能使用；学习效果还要看读者能否根据图与代码解释关键路径。不要把模板或图的存在当作已经理解机制的证据。
