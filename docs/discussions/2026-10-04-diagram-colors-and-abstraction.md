## 这次讨论要解决什么

用户希望系统总图能随章节逐步成长，尽量保留已有框架，不需要频繁返回上一章找图。用户倾向少压缩，同时希望弄清：哪些细节确实被某个模块包含，哪些结构应长期保留在总图中。

本轮先保存讨论，再从第一处具体问题做对照，判断是否值得采用这种修改。

## 已经采用的约定

- S01 建立基础系统，功能节点全部蓝色。
- 后续章节采用上一轮总图、本轮总图、最小核心图的三图结构。
- 第一张沿用上一章的节点、位置和连线；以本轮变化为参照重新配色，不提前添加新模块。
- 蓝色保留；橙色表示旧对象将被改造／改造后的实现；紫色表示本轮新增；红色表示真实移除。
- 旧细节首次展开不等于功能新增，应标明原有来源。
- 目前灰色虚线框用于提示下一张的细节合并，图注说明去向。
- 每张图旁边都有带实际色块和线型的图例。修改颜色或含义时，同步修改图、图例文字及图例样本。

## 检查发现的第一处问题：文件工具不能只“合并到 TOOLS”

当前 S03 总图不再单独画文件工具框，用 TOOLS 中的文字说明它们仍存在。这个表达混合了不同职责：

| 代码中的对象 | 实际职责 |
|---|---|
| `TOOLS` | 保存模型可见的名称、描述和输入 schema |
| `TOOL_HANDLERS` | 保存工具名到本地函数的映射 |
| `run_read`、`run_write`、`run_edit`、`run_glob` | 执行具体文件操作 |

因此，工具定义包含文件工具的说明，不等于它包含或执行文件工具的全部实现。原先“文件工具合并到 TOOLS”的图注不够精确，容易让读者误解归属。

本次建议：保留“文件工具实现：读／写／编辑／查找”这个小框，与执行入口建立关联；TOOLS 继续明确表示模型侧的工具定义。四个函数的内部代码可以不画，能力组本身目前不必省略。

核对依据：本地 `learn-claude-code/s02_tool_use/code.py` 中的工具函数、`TOOLS`、`TOOL_HANDLERS` 和 `agent_loop`。这里讨论的是已有实现的画法，没有给系统增加新能力。

## 对总图成长方式的建议

允许有限的内部折叠，但不要每讲完一章就把新增机制收成一个不透明的框。优先顺序如下：

1. 保留原节点，适度扩大画布。
2. 明确模块归属与接口，再考虑是否需要分组。
3. 内部细节确实妨碍阅读时再折叠，并保留成员名称或职责摘要。
4. 后续章节需要讨论内部机制时，在本轮总图中展开；回顾图仍沿用上一章结构。

判断折叠是否合适：读者是否仍能看出谁调用它、它处理什么、结果交给谁，以及它是否会改变主流程。若这些关系丢失，折叠就过度了。

| 内容 | 总图应保留的结构 | 可考虑折叠的内部细节 |
|---|---|---|
| 消息历史、模型请求、响应判断、工具执行、结果回传 | 主流程和回环 | 每一步的代码实现 |
| SYSTEM 与工具定义 | 进入模型请求的位置 | 提示正文、完整 schema |
| 工具分发与文件工具 | 分发关系、能力名称 | 单个函数的内部操作 |
| 权限检查 | 执行前的位置、允许与拒绝路径 | 规则列表与匹配过程 |
| Hook | 输入、执行前后、结束等触发位置 | 不影响主流程的具体回调清单 |
| TODO、Memory 等状态 | 状态及其读写位置 | 字段、序列化与校验细节 |

## 颜色机制尚待完善的部分

### 展示粒度与系统变化可以同时发生

一个模块可能既被修改，又在总图里折叠。当前实现把 `modified` 与 `folded` 视为互斥，尚不能表达这种组合。

待讨论的方向：颜色继续表达系统变化，例如保留橙色；灰色小标签说明“内部已折叠”。先用具体场景判断是否需要推广，不增加新的系统变化颜色。

### 容器变化不应被理解为整个算法重写

例如分发表增加一个映射，并不必然改变分发算法。橙色大框若覆盖整个执行层，应注明实际变更是“分发表增加一项”，避免夸大改动范围。

### 紫色需要区分图的用途

演化图目前用紫色表示新增，普通机制图用紫色突出本节核心。建议逐章演化系列坚持“紫色＝本轮新增”，重点通过局部图和文字说明；其他类型图应明确自己的图例。
