# 推荐阅读顺序：先核心，后补前置

这份 reference 保留用户提供的方法，并说明如何应用到具体问题。原文中的“原子核”用于比喻当前最能解释目标的部分；实际推荐以源码职责为依据。

## 应用时抓住三件事

1. **先有整条骨架，再选择一个核心动作深入。** 扫过七个步骤只需要知道各自职责，不意味着随后必须从第一个步骤开始逐项深读。
2. **从核心动作反查必要前置。** 先知道它要什么、做什么、交出什么，再带着问题去看数据或运行条件在哪里准备；不把所有创建过程变成强制前置课程。
3. **核心随问题变化。** 想看 Agent 怎样启动，可以先看 Harness；想看消息怎样转成模型输入，可以先看 Adapter；想看分数为什么不对，可以先看评测。每次说明选择理由和停止位置。

前置是当前调用成立的条件。先按接口理解这些条件，并不表示它们不重要或不再阅读。必要前置如果尚未理解，先补最少的关系，再返回核心动作。

这是一个非常毒辣、而且直击软件架构阅读本质的好问题！

之所以把重点放在 步骤 4（harness.run），背后有两个维度的原因：一个是刚才对话的上下文，另一个则是大厂架构师阅读代码时最关键的**“原子核原则（The Nucleus Principle）”**。

### 原因一：直接原因（上一轮你点名了它）

在上一轮提问中，你的问题原话是：

> “那么请你给出这里如果你要分析 harness run 你会看哪些内容吧”

所以我专门针对你指定的这个函数，进行了深度的实战拆解。

### 原因二：架构层面的深层原因——“这 7 个步骤的地位是极度不平等的”

如果在真实的业务场景下，即便你没有提要求，任何一个资深工程师在看完这 7 个步骤后，也一定会第一优先冲向 harness.run。

为什么？因为这 7 个步骤在系统中的信息密度和重要程度有着天壤之别：

```text
步骤 1: adapter.open_session()       ┐
步骤 2: boot_agent_sandbox()         ├─ 【低价值区：管线与脚手架 (Plumbing)】
步骤 3: swe.prepare_workspace()      ┘  （无非是起容器、建目录、拉 Git 分支，毫无新意）

步骤 4: harness.run()                ★ 【绝对核心区：系统的原子核 (The Nucleus)】
                                        （整个仓库为什么叫 "Coding Agent"，全在这个函数里！）

步骤 5: swe.git_diff()               ┐
步骤 6: swe.run_evaluation()         ├─ 【中等价值区：收尾与结算 (Settlement)】
步骤 7: adapter.finish_session()     ┘  （把代码拿去跑测试算分、打包发走）
```

### 原因三：避免“认知带宽耗尽陷阱”（The Cognitive Depletion Trap）

很多初学者读代码遵循**“线性执念”**：必须从第 1 步读到第 7 步。

这会带来一个极其致命的恶果：

1. 你先去读 步骤 1，你陷在 aiohttp 连接池和路由字典的琐事里；
2. 你接着读 步骤 2，你陷在 Sunabako 怎么用 PRoot 挂载虚拟目录、Linux cgroups 怎么设内存限制里；
3. 你接着读 步骤 3，你又在看怎么处理 Git detached HEAD、怎么解压压缩包；
4. 结果：你还没看到“Agent 到底是怎么思考、怎么调用工具、怎么把数据打回给模型的”，你大脑的电量就已经被前 3 个步骤的枯燥运维代码耗尽了，最后草草放弃。

### 原因四：资深工程师的“向心跳跃法”（Inside-Out Reading）

大厂工程师阅读复杂流水线，永远是先看“心脏”（核心动作），再倒回来看“血管”（外围支撑）：

1. 先击穿最核心的步骤 4（harness.run）：
   - 搞清楚核心矛盾：原来 Agent 是通过 ANTHROPIC_BASE_URL 假装访问外网，把流量打回本地的；
   - 看到它需要一个 session_id 和一个 adapter_url。
2. 带着答案倒回来看步骤 1 ~ 3：
   - 这时你再看步骤 1，你一眼就懂了：“哦！原来步骤 1 费劲弄的那个 session_id，就是为了后面塞给步骤 4 的环境变量用的啊！”
   - 这时看步骤 2 和 3，你只花 10 秒扫一眼就够了：“不过就是在起个容器把 Git 代码 clone 进去而已，跳过。”

### 总结一句话

“不要按代码执行的物理时间顺序去读，要按代码的‘业务价值密度’倒叙去读。”

抓住了步骤 4 这个最值钱的“心脏”，前后围绕着它打转的 6 个仆人步骤，在你的眼里瞬间就变得一目了然了。

## 应用边界与源码核对

- 上面的“上一轮点名”保留为所提供说明中的上下文，不据此替当前用户确认新的阅读步骤。
- “任何工程师”“永远”“10 秒”是原文的强调表达，不作为阅读顺序、时间预算或掌握状态的证据。最值得先读的模块随当前问题变化。
- `BaseHarness.run` 组织上下文、配置与启动等待；Agent 的模型请求和工具循环还涉及运行中的 CLI、Adapter 与其他组件。具体边界见 [Coding Agent 实例](coding-agent-order.md)。
- `ANTHROPIC_BASE_URL` 在这里配置的是 CLI 请求的 Adapter 地址。“假装访问外网”不是准确的接口职责说明；地址本身也不保证总在本地。
- 原文对连接池、PRoot、cgroups、解压与会话来源的举例不作为这些函数的已核对实现。遇到对应问题时，应回到具体版本的函数核对。
- 前置、评测与隔离机制的价值不由它们排在第几步决定。当前问题是奖励正确性或测试隔离时，这些部分就是主要阅读入口。
- 学习者可以先建立调用的输入输出模型，再逐渐展开前置；明确不知道的输入仍需补清，不能把“先跳过”记成已经理解。
