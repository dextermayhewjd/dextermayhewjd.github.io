# 源码阅读：推荐下一处入口

已有任务骨架后，围绕当前问题选择最值得先读的调用，再按需补前置和下游。阅读顺序服务于理解目标；代码执行顺序继续作为解释交接的依据。

## 读取当前上下文

先读目标仓库的阅读约定、项目入口、唯一进度记录及当前步骤，确认目标、已读历史与明确未知。已有骨架直接复用；需要建立骨架时使用 [repo-reading-scope](../repo-reading-scope/SKILL.md)。

用户已经指定本轮函数时沿用该范围。用户是在比较入口时，给出候选与理由；推荐本身不代表已确认开始下一步。保存到当前步骤或讨论指定的位置，不另建一套实时进度。

## 推荐方法

1. **把大目标收敛成当前问题。** 例如“理解 Coding Agent”之下，这轮是想看它怎样启动、怎样请求模型、怎样执行工具，还是怎样获得评分。
2. **从骨架中找直接回答问题的核心动作。** 优先选择能揭示当前关键关系的函数，核对真实职责与调用。不要按列表编号自动从头深读，也不要把某个固定位置永久视为最高优先级。
3. **先看核心，再补必要前置。** 先建立当前调用的最小输入、职责和输出模型，再回查理解这些输入所必需的创建处。只需知道“已准备好”的条件先列为边界；直接妨碍理解的概念先补清。
4. **沿实际交接继续。** 看清后返回骨架，再选下一个问题。跨 CLI、HTTP 或回调时明确运行边界；不要把时间上的交互误写成普通的直接函数调用。
5. **限制一轮展开量。** 遵循既有剪枝方法，从选定入口向下最多追两层，理解当前交接后返回。后续问题与本轮已解决的问题分开。

详细依据与用户原文见 [先核心、后前置的阅读方法](references/inside-out-method.md)。

## 输出一份短推荐

推荐包含以下内容即可，通常用几段话或一张小表：

| 内容 | 写清什么 |
| --- | --- |
| 当前问题与首选入口 | 优先看哪个真实函数；它怎样直接回答这个问题 |
| 最小前置 | 读它之前要知道哪些输入与场景；哪些创建细节可稍后回查 |
| 阅读范围与停止位置 | 本轮看清哪项职责或交接后就停 |
| 回到主线 | 读完回到哪里；下一项候选解决什么问题 |

必要时给一两个备选入口并说明适用问题。保留源码定位与版本，参数只展示推荐理由需要的部分，不把所有函数、配置和前置展开成新清单。

## 判断边界

- “原子核”“向心跳跃”可作为用户方法的比喻；推荐理由落在具体问题与源码职责上，不写成所有资深工程师必然遵守的定律。
- 前置、隔离、评测、清理都可能成为当前任务的核心。它们是否先读由问题决定，不以“脚手架”“低价值”一概跳过。
- 启动器通常交接给真正执行任务的组件。定位到启动器后，要说明哪些行为发生在外部 CLI、服务或回调中，不能把全系统能力归入一个函数。
- 推荐顺序与实际确认分别记录。只有用户确认本轮问题与范围后，才按既有流程展开源码并建立函数记忆；已明确指定的范围不重复询问。
