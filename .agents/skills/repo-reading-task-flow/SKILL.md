# 源码阅读：本步任务链路总结

围绕已确认的 scope，把读过的部分连成一条可跟随的任务链路：接住什么、各部分怎样交接、最终得到什么、再回到哪里。总结依据实际阅读与讨论形成；稳定格式帮助读者回顾，不代替理解过程。

## 按用途读取 reference

创建或整体修订 task flow 时，先读 Step 003 的完整结构；涉及入口函数下的多层调用时，再读 Step 007，重点看第 2 节。

| Reference | 参考什么 |
| --- | --- |
| [Step 003：会话轨迹与奖励怎样交成训练样本](references/step-003-trajectory-to-samples.md) | 用户指定的整体结构主样例：四部分正文、调用后的数据变化、卡片导航及折叠来源。 |
| [Step 007：启动 CLI 并等待结束](references/step-007-harness-call-hierarchy.md) | 用户新认可的调用层级样例：先看入口的直接部分，再逐支展开子调用，同时看清作用、结果与返回。完整保留原 task flow。 |

复用样例的组织方式；函数名、主分支数量、展开深度、结果字段和源码行号按目标步骤核对。Step 007 的四个主分支属于该函数，不能套成所有任务的四步。样例中的 Slime 版本与已读状态仅属于原记录。

## 定位本次总结

读取目标项目入口、唯一进度、当前 `01-scope.md`、本步使用的函数/类卡片及相关 `04-flow.md`。确定本步的输入、关键交接、终点和仍未展开的部分；缺少交接证据时按需回查对应版本源码，保留真实符号、具体实现与行号。

已有明确的总结请求直接执行。尚未读清的交接如实注明；不为填满总结而自动展开新函数或开启下一步。用户认可排版、文件生成或源码核对，不等于用户掌握了全部实现。

## 固定结构

标题写本步完成的具体任务；开头用一段 `>` 概括“接住什么 → 关键处理 → 交出什么”，随后链接本步 scope、函数记录和形成过程。

正文按以下四部分组织。标题可随任务调整，四部分职责保持稳定。

| 部分 | 要写清楚的内容 |
| --- | --- |
| 1. 本步在任务中的位置 | 前序已经给出什么、采用哪个场景或分支、从哪里进入、到哪里结束。简短承接 scope。 |
| 2. 已读部分怎样完成交接 | 按实际执行过程串起关键调用或阶段：输入/触发 → 动作 → 数据或状态变化 → 下一站。保留必要源码位置和函数卡片入口。 |
| 3. 本步结果的含义与去向 | 最终返回的数据、保存的状态或交付的资源是什么，来自哪里，后续由谁使用。优先沿用卡片中已有的小例子。 |
| 4. 本步的收束与后续衔接 | 已经覆盖到哪里、仍有什么未知、进一步展开的条件，以及返回整体主线的位置。下一步候选与用户确认分开。 |

末尾用 `<details>` 折叠保存源码版本、固定链接、形成依据与验证范围。区分静态核对、构造示例、替身验证和真实运行；原话与纠正过程链接回 `04-flow.md`。

## 第 2 部分怎样画清楚

- 当本步围绕入口函数及其嵌套调用展开时，以可见的调用层级图作为主展示：根节点是入口，第一层是它直接执行的关键部分，各部分下面再展开各自的子调用。读者应能先看清主体，再沿一个分支深入。简单链路或以跨进程交接为主的任务，可采用短代码或时序图。
- 子调用留在真实调用者下面，不与入口的直接部分平铺编号。构造上下文、读取状态等关键语句也可作为一个部分，注明其作用即可，不为凑层级另造函数。
- 关键节点同时交代“谁接到什么、做了什么、交给谁”。缩进表达调用归属，编号按源码说明执行顺序，旁注交代作用、结果和返回位置；条件与并发关系应明示，不能仅凭上下排列暗示先后。
- 顺序表可补充定位，但不能代替这类任务的层级图；已有主图时，将重复的逐项源码对照折叠。卡片链接紧接主图，便于从分支进入对应函数。
- 标明具体文件与符号，关键交接保留行号。共同实现与具体子类分开定位，避免读者在同名 `common.py` 或 `run` 之间猜测。源码链接固定版本；卡片链接放在相应节点附近或图后紧接处。
- 嵌套调用写清返回父函数后继续哪一处。遇到等待、回调或跨进程通信，标明谁仍在运行、谁在等待、什么触发继续；例如 CLI 的请求发生在等待其退出期间。HTTP 或回调触发的处理应标明触发关系，不能画成调用树中的普通直接调用。
- 将交付与结束分开：交出资源后可能仍有使用期；后台任务启动返回也不等于任务完成。结果进入多个接收方时，各自标明去向。
- 展开到能解释本步交接为止。token 拼接、重试、`inflight` 容器等细节由对应卡片承接；只有当前问题需要解释其影响时，才在主线保留相应状态变化。

## 结果展示按任务调整

第 3 部分可以是输出字段及来源表、登记后的状态小例子，或“交付 → 使用 → 回收”的资源说明。无需把所有结果都写成返回值。

需要对照变体时，再读 [Step 004 的状态登记](../../../00-repo-reading/repositories/slime/steps/step-005-agent-preparation/05-task-flow.md)或 [Step 005 的资源生命周期](../../../00-repo-reading/repositories/slime/steps/step-006-agent-sandbox/05-task-flow.md)。它们补充主 reference，不增加所有步骤都必填的栏目。

## 保存前核对

- 从本页能追踪输入、关键变化、输出/副作用和后续接收方，调用及返回顺序可跟随。
- 对嵌套调用，读者能在图中区分入口的直接部分与内部子调用；表格没有替代主图，分支数量和父子关系符合源码。
- 主文没有越过 scope 的停止位置展开新主题；边界之外只保留必要接续。
- 源码与卡片链接有效，版本归属清楚；例子与相应卡片一致，未知仍被保留。
- 沿用项目实际文件位置；已有总结按用户要求修订，其他步骤与原 reference 保持其历史归属。
