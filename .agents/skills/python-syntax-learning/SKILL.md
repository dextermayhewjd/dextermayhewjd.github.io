# Python 语法：从最小知识点逐步建立理解

让读者读完能够独立复述事实、预测执行结果、辨认对象。篇幅服从这个目标：必要的新关系讲透，已知或附带信息简短交代；既不堆概念，也不一味删短。

## 1. 确定本课的最小边界

1. 从对话和前文确认读者已经掌握什么、当前卡在哪里。沿用已确认的基础与阅读路线；信息不足时，先声明少量必要假设，只有影响起点的歧义才询问。
2. 先在工作草稿中列出本课能带走的**原子知识点**：每条是一句可独立判断、复述或用代码验证的事实。例如“调用生成器函数会创建生成器对象”，而非“介绍生成器”。数量按概念需要确定。
3. 按知识依赖排序，找出足以回答当前问题的最小一组。课程编号只表示阅读顺序；前置要从本课实际复用的概念、行为和例子中确定，可以来自更早的多节课。新知识如果依赖尚未学过的东西，先补这个前置关系，或安排为下一课；不要把新的执行入口、对象或机制冒充背景知识。
4. 分清主要新关系与辅助信息。定义、参数或返回值若读者已熟悉，只需一句；创建与执行等容易混淆的关系，才用同一例子展开验证。
5. 引入新语法或机制前，先说清旧方案已经能完成什么，再给出具体的新增条件或要求。区分“旧方案无法做到”和“旧方案可以做到，但需要调用方手动组织或承担额外责任”；不要为了引入新 API，虚构旧方案的局限。
6. 用这个差距提出本课问题，让读者在看到新机制之前就明白为什么需要它。先描述需要满足的行为或约束，再引入解决它的语法；不要把“能否改用某个新 API”当作需求本身。沿用同一例子，指出新增机制具体改变了哪项能力或责任；每个学习单元只展开必要的一层。

### 提问与方案选择

需要确认学习起点或呈现方式时，用聚焦的问题让用户选择；沿用已经确认的偏好，不为每课重复确认。用户要求逐项讨论时，一次先解决一个影响后续写作的问题。

每个选项都给出可直接想象成品的简短实例，并说明与其他选项的关键区别、优点和代价、适用情况。尽量用同一内容演示不同方案，避免只有抽象名称。给出推荐及理由，但保留用户选择；已明确的要求直接执行。

按当前问题只读取对应参考，不默认加载全部；这些例子用于判断依赖，不是固定课程目录：

- 首次解释协程的创建与运行：[协程的最小边界](references/coroutines.md)。
- 解释生成器的调用与推进：[生成器的最小边界](references/generators.md)。
- 解释装饰器，判断函数对象的前置知识：[装饰器的最小边界](references/decorators.md)。
- 承接旧课、说明为什么新增机制：[新机制如何承接旧方案](references/introducing-new-mechanisms.md)，含 TaskGroup 对照。
- 写章节开头、连接已学知识或说明新机制的动机时，先读 [从已学内容连接到新问题](references/lesson-transition.md)：先定位真正复用的旧知识，再用独立的连接说明引出本课问题，按内容决定是否使用图和代码对照。

## 2. 用一份最小例子提供证据

1. 选择能暴露核心区别的一个问题，让读者先猜结果。沿用同一份数据、函数和变量，新增机制时只改与问题有关的部分。
2. 默认正文用一份完整可运行的主例子。删去无助于当前知识点的业务框架、嵌套 helper 和先进写法。确需对比时，明确前后只改变了什么。
3. 把名称对应清楚：函数、调用生成的对象、执行入口、返回值分别是什么。根据语法实际行为区分定义时、调用时、开始执行时、暂停或退出时；不要把这些阶段混成一步。
4. 有源码背景时先核对用户指定版本，保留真实接口并说明教学裁剪；没有项目背景就用标准库独立实验，不引入虚构项目依赖。
5. 核对 Python 版本，运行例子验证输出；不能运行时标明“预期输出，未执行”。代码展示与下载文件保持一致。验证语义，不用计时快慢证明不确定的调度顺序。

### 关键代码必须有紧邻注释

教学代码首次引入接口，或涉及状态变化、等待、通知、超时、资源进入与退出时，必须在对应行末或紧邻上方写简短注释。此规则同样适用于主例子、对照片段和补充小实验；不能只把解释放在代码块之后、表格或图中。

注释按当前步骤说明“为什么做、操作哪个对象、发生什么变化”。涉及等待时，说明谁在等什么、什么时候继续；涉及返回值或输出时，说明 `True`、`False` 等结果的具体含义。优先解释本课新增或容易混淆的关系，已熟悉且含义直接的普通语句无需逐行重复。网页代码与可下载文件的注释也要保持一致。

例如，通知标志的小实验应直接写清楚：

```python
stop = threading.Event()     # 创建通知对象，初始标志为 False。
stop.set()                   # 发出通知，把标志设为 True。
print(stop.wait(timeout=0))   # 不花时间等待；已有通知，打印 True。
stop.clear()                 # 重置为 False；不会重新启动已结束的线程。
print(stop.wait(timeout=0))   # 没有通知且等待时间为零，打印 False。
```

## 3. 正文采用编号层级

按以下阅读次序组织，随内容多少合并小节：

1. **与已学内容的连接、问题与例子**：开头单独放一段简短的“与已学内容的连接”，明确写出复用的旧知识及本课新增的问题。有对应旧课时链接到相关讲解，并用一句具体行为唤起记忆；无相关旧课时说明实际需要的基础，不编造承接。不要只列课号或 API，也不要因编号相邻就强行承接上一课。随后给出问题、主代码和简短输出。新旧对比围绕同一需求，避免只列两套语法。
2. **沿执行过程解释**：顶层用 `1. 2. 3.` 区分阶段；阶段内再缩进列出行为与对象变化。只有真实执行有先后关系时，编号才表达时间顺序。
3. **带走的原子结论**：编号列出独立事实，并给一两个需要预测结果或辨认对象的自查问题。下一课只指出将新增的问题。

例如“定义时 → 调用时 → 运行时”是三个阶段的组织方式，不要求所有语法都套这三个标题。`with` 可按进入、使用、退出解释；装饰器需要分清装饰发生时与被装饰函数调用时。

核心解释与末尾结论可以相互对应，但不要再复制一份完整的长篇详解。压缩时删重复，保留能解释“为什么得到这个输出”的关键步骤；新知识点较多时拆课，而非用折叠把必要基础藏起来。

## 4. 区分必读理解与可选材料

1. 默认阅读包含理解主例子所需的一切。源码回查、项目应用、全部位置清单、高级边界放在主线之后；网页中将它们合入一个默认收起的“按需阅读：项目应用与源码位置”。
2. 折叠只是呈现方式，不改变原文、代码和来源的身份。调整已有材料时保留有效内容、锚点和下载；用户要求删去重复讲解时，不再用另一份折叠长文重复它。
3. 普通聊天直接在对话回答；用户要求文档或页面时才写入对应位置。写入网站时遵守项目预览与构建规则，核对实际渲染、列表层级和折叠。不要因使用本 skill 自动改写整套课程或创建项目专用目录。

## 5. 交付前自查

1. 每条原子结论能否指出例子中的证据？范围与措辞是否准确，是否把本例行为误写成语言的唯一执行方式？
2. 每个新符号是否已解释，或属于读者明确掌握的基础？是否在第一课提前讲了下一课的机制？
   开头的连接说明是否独立可见，并指出旧知识在本课怎样继续使用？旧课引用是否来自实际依赖，而非编号相邻？
3. 读者能否在新机制出现前，说清旧方案已经能做什么、本课多了什么要求、新机制接管了什么？是否误把手动组织的负担说成旧方案根本做不到？
4. 编号和缩进能否让读者看清阶段与子步骤？定义顺序、调用顺序和函数体执行顺序是否混淆？
5. 输出、变量身份、返回值、必要异常边界是否一致？关键代码旁是否已说明本步目的、状态变化或等待条件，而非要求读者跳到下文寻找解释？本课是否仍聚焦当前问题？
6. 交付时给出本次改动范围、阅读入口和实际验证结果。构建通过只证明材料可用，不代表读者已经理解。
