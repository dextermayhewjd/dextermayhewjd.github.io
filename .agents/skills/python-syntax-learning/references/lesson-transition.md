# 从上一课过渡到新问题

适用于学习动机已经明确，但图或代码前的说明仍显抽象、读者不知道为什么要看下一个例子的情况。若尚未说明新机制解决什么，先参考 [新机制如何承接旧方案](introducing-new-mechanisms.md)。

## 1. 用三步接住读者已经知道的内容

1. **上一节已经会了：** 用一句话说明旧方案能够完成的具体工作。
2. **现在多了一个要求：** 只指出本课新增的调用层级、执行条件或管理责任。
3. **先尝试原来的办法：** 提出可判断的问题，再让读者看图和代码，观察原方案在新条件下会怎样。

第三步不预先宣布新 API 的名字。问题先落在需要完成的行为上，下一部分再引入解法。按实际内容合并步骤，不必每课机械套用同样的三句标题。

## 2. await 的三步引入

可用的问题式标题：**在协程里面，还能继续用 run 吗？**

2. **现在多一层调用：** 一份正在运行的协程，也需要调用另一份协程，并取得它的返回值。

## 3. create_task 的三步引入

1. **上一节已经会了：** 用 `await` 等待一份协程，取得结果后再继续下一行。
2. **现在多了一个要求：** 两份工作互不依赖，希望一份等待时，另一份也能开始并推进。
3. **先尝试原来的办法：** 连续写两行直接 `await`，能满足这个要求吗？先观察它们的执行顺序。

这里的旧代码是合法的，也能取得两个结果；问题是顺序调用让第二份协程在第一份返回后才开始，没有满足等待可以重叠的新要求。先指出这个差距，再引入 `create_task`。

“尝试旧法”不一定得到异常。应按实际情况说明它是无法运行，还是能够运行但没有满足本课的新要求；不要为了形成转折而把有效代码称作错误示例。

## 4. 图与代码各承担一件事

1. **图展示关系：** 沿同一次调用画出“外部代码 → 启动外层协程 → 内部还需要另一份协程的结果”。在尚未讲解的步骤处保留问号，避免只是把几种状态并排罗列。
2. **代码定位问题：** 沿用前文的函数和数据，将读者自然会尝试的旧写法放到对应位置；说明它是无法运行，还是能运行但不满足新增要求。错误示例应明确标注，不能冒充本课的正确运行示例。
3. **文字解释限制：** 图下只解释必要事实，结尾留下“怎样执行这份协程并取得结果”的问题，下一部分用新语法回答。

## 5. 核对呈现和边界

1. 图上方应先让读者知道“之前能做什么、现在变了什么、为什么尝试这份代码”，再出现具体图示。
2. 保留前文有效的例子和讲解，优先修改过渡与问题描述，不因改进开头而重写整课。
3. 检查网页中实际显示和复制出的 Python 代码，保留缩进、换行和脚本入口；完整独立脚本按前文约定使用 `if __name__ == "__main__":`。
4. 错误尝试需要核对实际失败原因；正常路径的例子只能支持正常路径的结论。
