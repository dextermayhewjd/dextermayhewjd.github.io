# 阅读系统的 skill 分工建议

2026-10-20。用户最初选择：“先独立短期 memory，其余先列分工建议”；随后明确要求把当前 scope 的三段结构与剪枝方法单独做成 skill，并继续要求独立推荐阅读顺序。当前已建立短期 memory、scope 与 order 三个 skill；下表其他职责继续保留为候选。

用户加入两条代码阅读指南后，最新调整建议见[按指南重新设计阅读步骤](guide-based-redesign.md#skill-分工建议)：步骤组织暂时同时承担主线与实际过程记录，不急于独立过程 skill。本文保留此前候选划分供对照。

## 本轮已落实

[repo-reading-order](../../../.agents/skills/repo-reading-order/SKILL.md) 负责已有骨架后推荐先深入哪里，说明目标、理由、最小前置和停止位置。它保存“先核心、后回查”的方法，推荐结果仍由用户确认；不自动新建步骤或函数记忆。

[repo-reading-scope](../../../.agents/skills/repo-reading-scope/SKILL.md) 负责本步阅读目标、指挥官函数与核心骨架，配有[详细剪枝方法](../../../.agents/skills/repo-reading-scope/references/pruning-method.md)和 [Coding Agent scope 样例](../../../.agents/skills/repo-reading-scope/references/coding-agent-scope.md)。它只承接 scope 这一部分，不表示下表整个步骤编排 skill 已经建立。

[repo-reading-short-term-memory](../../../.agents/skills/repo-reading-short-term-memory/SKILL.md) 负责本步 `02` 中的单函数记录与索引，包括原话、场景、输入输出、LLM 模型、未知和来源。

共同记录已完整覆盖具体实现的本轮场景时，具体实现保留引用入口，索引直接指向共同记录。本次 Anthropic → BaseAdapter 的整理属于这项职责。

新 skill 直接引用原有模板与已认可样例；样例、历史笔记和当前步骤内容不随 skill 拆分重写。[repo-reading-memory](../../../.agents/skills/repo-reading-memory/SKILL.md) 保留为总入口，短期工作交给新 skill，尚未拆出的长期规则继续留在原处。

## 其余职责的候选划分

| 候选 skill | 何时使用 | 负责的产物 | 分工边界 |
| --- | --- | --- | --- |
| `repo-reading-step` | 讨论这一步要读什么，或接续下一步时 | 步骤 README、`01-scope.md`，以及项目的唯一进度入口 | 确定函数、当前问题、必要基础、主线与停止位置；组织记忆工作，不代写用户理解 |
| `repo-reading-long-term-memory` | 已确认进入下一步，需要带入已有函数认识时 | 新一步的 `03` 及其索引 | 合并上一步 `03 + 02`，保留内容、未知、作者、认识时间和来源；本步的新认识仍由短期 skill 写入 `02` |
| `repo-reading-process`，是否独立仍待讨论 | 保存实际问题、解释与理解修正过程时 | `04-flow.md` 及按需引用的扩展说明 | 追踪问题与证据怎样形成或修正认识；最终函数模型由短期记录维护，避免重复讲解 |

这些职责现在仍由既有[工作流](../../../00-repo-reading/workflow.md)和记忆总入口承接，不因列出候选名称就视为已经建立或启用。

## 后续怎样逐项确定

每次选一个实际操作来检查边界：例如“进入下一步并继承已有函数”，看它需要读取什么、写入哪里、交给哪个已有职责。能独立触发且有明确产物时，再考虑拆成 skill。

先明确长期继承与步骤编排的交接；“形成过程”是否需要独立 skill，继续依据它相对函数记忆提供的独有内容判断。文件夹数量不决定 skill 数量，也不新增一套与项目路线并行的进度。

选步还需要一个读前定位环节：助手先查看任务入口和候选函数的接口，判断哪些未知是当前问题的必要前置，哪些可以暂按接口接受，再提出“要解释的问题、候选函数、选择理由、暂时接受的条件和停止位置”，由用户确认。不能要求用户在尚不了解候选函数时仅凭函数名决定顺序。具体讨论见[先读 run 还是消息转换](discussion.md#怎样判断先读-run-还是消息转换)；目前仍为待验证建议。

提出候选前还需检查最小阅读前置：用户是否知道输入对象是什么、为什么需要、结果怎样交回。若这些关系尚不清楚，先把缺少的前置作为候选单元，不能只标“暂时接受”就直接进入实现。详见[run 的最小调用场景](discussion.md#进入-run-之前仍需建立最小调用场景)。

用户随后指出启动前置过多，倾向从 `_run_turn` 的局部开始。选步不应默认沿外层启动链展开；可以用边界清楚、输入输出可呈现且前提较少的局部承载主线，每步只展开其中一个问题，详见[以一次模型请求组织主线](discussion.md#缩小起点以一次模型请求组织主线)。这仍是待共同确定的步骤编排方法。
