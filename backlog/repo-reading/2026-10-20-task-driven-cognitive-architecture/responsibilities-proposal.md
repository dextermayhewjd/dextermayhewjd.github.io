## 1. 整体分为三类职责

| 部分 | 负责回答的问题 | 保存的内容 | 对应位置 |
| --- | --- | --- | --- |
| 阅读导航 | 这次为什么读这里，读到哪里就够了？ | 当前任务、本步问题、已知入口、展开范围、停止条件 | 项目目标与本步 `01-scope.md` |
| 知识模型 | 目前怎样理解代码，以后如何直接复用？ | 函数卡片，以及函数之间的交接和任务整体关系 | `02`、`03` 中的 `functions/` 与 `overview.md` |
| 学习记录 | 哪个问题被澄清了，依据是什么，还有什么没有确认？ | 关键提问、实际反馈、模型变化及证据入口 | `04-flow.md`；较长的材料按需链接到 `references/` 或原讨论 |

日常接续优先使用阅读导航和知识模型；需要回查某条认识的来由时，再打开学习记录。这是职责建议，不要求每次按顺序读完所有文件。

## 2. 知识模型内部再分为函数与组合关系

### 函数卡片：解释一个可复用的局部

保留当前 common 样例中的核心内容：使用场合、调用代码、成对输入输出、简短 LLM 模型、用户原话、未知和来源。它应让人能够判断这个函数在当前任务里有什么用，而不必重看完整讲解。

以 `_translate` 为例，卡片负责说明：请求 `body` 被整理为 `translated` 与 `tools_schema`；前者是系统指令和对话历史，后者是可用工具及参数定义；这里不执行工具。具体例子与转换细节由这份卡片承担。

函数卡片可以保留几行调用来交代局部语境，但不在其中维护整个任务的完整调用链，也不重复叙述全部学习问答。

### 组合关系：解释这些局部怎样完成任务

`overview.md` 负责说明哪些函数在当前任务中相连、谁把什么交给谁、这次增加了哪条关系。函数目录仅用于查找，不能代替组合模型。

例如下面是已核对源码中的一段交接，只突出转换结果的去向，省略 tokenizer、session 和请求参数等其余输入：

```text
body
  → _translate
  → translated、tools_schema
  → _render_token_ids
  → prompt_ids
  → call_sglang_generate
```

这一层解释“两份转换结果共同参与渲染，生成的 token IDs 再交给生成请求”，链接相应函数卡片；不复制每个函数的完整输入输出样本。

源码定位：[固定版本 common.py 第 341 行起](https://github.com/THUDM/slime/blob/2f2318653f6f794dddd321eff7c9d4b7b174643f/slime/agent/adapters/common.py#L341)。这是源码关系示意，不新增用户已理解这些函数的记录。用户尚未表达的关系，仍应放在明确标注的源码参考中。

## 3. 短期与长期是同类知识在不同时间的记录

| 位置 | 时间范围 | 保存方式 |
| --- | --- | --- |
| 本步 `03-long-term-memory/` | 进入本步前已经积累的认识 | 保留已有函数卡片、组合模型、未知与来源，供本步取用 |
| 本步 `02-short-term-memory/` | 本步新增或修正的认识 | 保存有变化的函数卡片及新增或修正的组合关系；函数卡片保持完整可读 |
| 下一步 `03-long-term-memory/` | 合并到上一步结束时的累计认识 | 合并上一步 `03` 与 `02`，处理修正和冲突，保留未知与来源 |

短期与长期不各自发明一套知识格式；长期也不因为归档就代表已经掌握。未变化的函数不需要在每一步的 `02` 中重复抄写。旧步骤保留当时快照，不在整理下一步时重写历史。

## 4. 对形成过程的明确建议

**保留追溯能力，将形成过程收缩为关键学习事件的记录；函数文件里通过来源链接进入，不另写一遍函数说明。**

值得记录的事件包括：一个边界被明确确认、一个理解被纠正、一份新证据使模型发生变化，或一个影响后续阅读的问题仍未解决。普通展开讲解不必再完整复述到过程页；已有完整讨论可以直接链接。

每个事件只需交代：

1. 当时要澄清什么。
2. 实际查看的材料和用户反馈是什么。
3. 哪条认识被确认、修正或仍然留白，以及对应函数卡片或关系记录在哪里。

例如，现有记录中确实发生过“messages 含工具调用时，转换是否会实际读文件”的追问；用户回答“不会 这里的translate 只是作为一种格式的切换”。可以保留这一问题与反馈作为职责边界被确认的依据，再链接函数卡片。不能改写成“用户曾经误以为这里会执行工具”，因为用户没有这样表达。

不应在过程页再次放一套完整的 `body`、`translated`、`tools_schema` 样本和函数讲解；这些内容由函数卡片及其参考材料承担。关键结论可以用一句话提示，避免在两个地方维护整套解释。

该建议区分的是用途：函数模型用于直接恢复当前认识，过程记录用于追溯认识变化。已有完整问答与旧快照继续作为历史材料保存；收缩日常展示不等于删除历史。

## 5. 用一个步骤检查分工

假设本步要弄清“`_translate` 返回的两份结果分别是什么”：

| 放置位置 | 本步具体写什么 |
| --- | --- |
| `01-scope.md` | 当前问题、从已有 `body` 开始、先弄清两份结果用途，详细渲染机制暂不展开 |
| `02/functions/.../BaseAdapter._translate.md` | 使用场合、调用片段、代表性输入输出、职责边界、用户表述、未知、来源 |
| `02/overview.md` | 本步新增的整体关系；下游渲染入口可以标为已定位，是否已理解按实际反馈记录 |
| `03` | 本步开始前的累计模型，供查阅 |
| `04-flow.md` | 哪个问题被追问、用户怎样回答、据此确认了什么；链接模型和证据 |
| `references/` | 当前卡片不需要展开的长解释、完整样例等支撑材料 |

本步结束后，把新认识合入下一步的 `03`。若下一步实际研究渲染，再新增渲染函数卡片，并将“两份转换结果怎样用于渲染”的新认识写入该步的组合模型。一个步骤不必等于一个函数；步骤按当前问题划界。

## 6. 双方的分工

- **助手负责组织与核对。** 定位任务与源码，提供够用的局部材料，选择当前关键问题，区分用户表述和源码解释，维护记录、链接及继承。发现重复时由助手整理，不让用户重复填写文件。
- **用户负责提供实际反馈。** 说明当前怎样理解、哪里接不上、哪些地方需要展开，并指出整理是否失真。无需在每次阅读中复述全部旧知识，也不承担记忆文件的维护工作。

用户原话留在模型中，是为了明确哪些认识由用户实际表达；来源链接负责找到原始上下文。两者可以有必要的短句重复，但完整讲解只维护一处。以上建议的目标是让阅读时容易找到当前需要的信息，同时保留以后核对的依据。
