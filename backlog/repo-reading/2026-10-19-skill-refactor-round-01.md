## 这轮为什么只改进一件事

用户希望一起推演，并一点点重构 skill。我们先检查“如何选出不大不小的一步”，让具体试讲结果决定下一处改动。

当前 `code-reading-chapter` 已规定真实调用、输入输出、局部关系与返回位置；通用记忆和步骤目录由 `00-repo-reading/workflow.md` 维护。本次可见 skill 路径中没有独立的 `repo-reading-workflow`，尽管章节 skill 的描述曾引用这个名称。后续明确 skill 分工时需要处理这个悬空引用，不把当前工作流文档误称为已安装 skill。

本轮仅提出一条“先确定学习单元边界”的候选规则。未证明旧 skill 在独立应用时必然失败，也未把转换函数运行成功当成 skill 行为验证通过。

## 试讲样例的位置与边界

最小定位：CLI 发来模型请求，Adapter 将协议输入转成内部消息与工具定义，再交给后续处理。

| 项目 | 本轮选择 |
| --- | --- |
| 本步问题 | 一条普通消息和一个工具定义，如何从请求格式转成内部格式？ |
| 起点 | 已取得的 `body`，包含一条用户文本消息和一个工具定义 |
| 定位入口 | `BaseAdapter._run_turn()` 中的 `self._translate(body)` |
| 实际展开 | `AnthropicAdapter._translate`、`_translate_messages`、`_tools_to_chat_tools` 的本例路径 |
| 终点 | `translated` 和 `tools_schema`；知道下一接收方是 `_render_token_ids` |
| 保留到后续 | 其他消息类型、预处理和 Session 细节、分词、模型请求、响应、轨迹与清理 |

这些是当前样例的条件，不表示所有学习步骤都固定需要三个函数。若用户觉得这一步仍太大，可先只看普通消息，再补工具定义；若已熟悉转换，可以把下一处交接纳入。

## 一份真实格式的输入怎样变化

下列值为教学构造，不是实际 Agent 运行记录。完整请求仅保留本例用到的两个字段。

```json
{
  "messages": [
    {"role": "user", "content": [{"type": "text", "text": "列出当前目录"}]}
  ],
  "tools": [
    {
      "name": "list_files",
      "description": "列出目录中的文件",
      "input_schema": {"type": "object", "properties": {}}
    }
  ]
}
```

输出 `translated`：

```json
[{"role": "user", "content": "列出当前目录"}]
```

输出 `tools_schema`：

```json
[
  {
    "type": "function",
    "function": {
      "name": "list_files",
      "description": "列出目录中的文件",
      "parameters": {"type": "object", "properties": {}}
    }
  }
]
```

本步得到的关系是：文本内容块被整理成内部消息，工具参数定义被放入内部工具 schema。工具尚未执行；转换输出会作为后续模型输入处理的材料。

真正试讲时还需要沿对应源码说明这两个变化为什么发生。本页先让用户判断“这一组输入输出变化是否是合适的一步”，不把后续实现解释一次性写完。

## 给 skill 的第一条候选修订

> 写一段新的带读内容前，先明确本步的问题、已有输入、结束时的输出及接收方，以及留待后续的内部机制。围绕一份具体数据走通一个可解释的变化，按依赖选择必要函数。用户反馈跟不上时补必要前置或缩小范围；已经熟悉时合并普通细节。步骤大小由理解反馈调整，不机械按函数、文件或行数切分。

这条修订可落在章节 skill 的“共用阅读层次”之前，具体模板放在工作流的 `01-scope.md`。累计记忆的复制和目录规则继续由通用工作流负责，避免在多个 skill 中复制全文。

接下来先记录用户认为本例偏大、合适还是偏小，再调整候选规则与试讲内容。正式改动 skill 时另做相应的应用验证；本页是共同推演记录，不代替验证，也不代表用户已经理解转换实现。

## 后续反馈：已有页面的输入边界更合适

用户指定现有 Translate & Forward 页面作为参照，并明确目前只知道 `_translate` 将请求 body 变成 `translated` 与 `tools_schema`，其他环节仍不清楚。页面中的 generate 是定位条件，不要求从头读完整任务。

据此，推演改为沿用原页面的同一份完整请求，不再默认缩成“一个用户消息和一个工具”的另一个案例。具体的 [scope 与 flow 填写示例](./step-01-translate-preview/README.md)分别保存进入本步的认知边界，以及请求格式、转换路径和输出说明。

这次反馈说明候选规则还应区分“用户已理解”与“为了进入本步暂时接受的场景条件”。未知的上游允许作为边界保留，不能因出现在定位图上而自动记作已掌握。正式 skill 尚未据此修改。

用户随后进一步明确：先由助手定位，再由用户说模块做什么、为了什么。修订 skill 时应加入这一分工，而不是要求助手为每一步预写完整的转换解释。个人记录允许“知道作用，实现留白”；详细教材作为参考保留。
