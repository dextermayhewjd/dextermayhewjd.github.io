# 代码章节阅读模板

让读者沿一份具体数据，说明本章“从哪里接手、做什么、留下什么、交给谁”。统一理解方式；步骤数、分支和对象展开程度由真实代码决定。

## 先确定本轮交付

读取项目约定、已确认的模板和目标章原文，区分三种工作：

| 用户请求 | 本轮交付 |
| --- | --- |
| 把现有材料接入网页、点击即可阅读 | 原文和原图直接展示，仅做入口、路径及显示层调整 |
| 看看是否需要修改、整理一个对比版本 | 差异说明；按本次要求交付候选提纲或完整候选稿，与正式稿分开，提供比较入口 |
| 新写章节或采用已确认稿 | 在授权范围内写入，并核对源文件、图、示例和网页一致 |

用户批准入口接入，不等于批准改写内容。已有正文的改稿先比较，用户确认后才替换；同一已批准版本无需反复确认。纯材料审阅可以先进行。源码阅读先查已有仓库确认记录：已确定的路径持续沿用，包括后续章节；只有更换仓库、尚未确认或候选有歧义时才询问。版本与工作区仍需核对。网站工作先确认本地预览可用。

审阅网页显示时，同时检查页面入口与渲染模板，必要时打开预览。区分原 Markdown 的顺序与当前网页的顺序；不能仅凭原文件断言“首屏先显示哪张图”。未检查渲染层的显示问题标为待确认。

## 共用阅读层次

1. **阅读问题、简短导航与局部图**：先说明本章要回答的问题，再用短的缩进伪代码标出外层入口、当前职责和返回位置，随后展示当前职责的局部图。前后已读步骤用省略号带过；完整生命周期图作为可选定位层。
2. **把图接到真实调用**：给出调用者中的短代码骨架，让读者知道为什么进入这里。交代调用者、当前对象、输入与接收返回值的变量。源码摘录、删节骨架、说明性伪代码各自标明。
3. **沿一份数据逐步阅读**：每步按“为什么到这里／输入 → 当前职责与关键代码 → 输出或副作用 → 谁接着使用”解释。回到同一调用主线，不把全文变成 helper 清单。
4. **出口与复述**：把最终结果对应到下一步的实参或状态；给少量能暴露理解缺口的问题，而非让读者背字段名。

每章在局部图与目标之后、具体代码之前，先给出简短阅读语境：当前跟随哪层调用、本章展开什么、读完返回哪里。相邻章节可能在同一个函数内展开，也可能下钻到共用组件；不要用目录位置或章节编号推断执行顺序。列出本章主要源码文件及其职责、入口符号和行号，放在默认收起的入口中。文件范围以本章职责为准，不要求通读整文件；整体编排函数也不等于承载全部实现。

导航块明确标为阅读伪代码，通常控制在一屏内，只定位当前层，不提前展开后文的分支、参数和循环实现。缩进可以表示调用下钻或任务中的交互范围，要说明异步 HTTP 边界，不能把外部 CLI 的循环写成 `generate()` 内的真实同步调用。导航伪代码与真实摘录分别记录；核对原稿源码是否保留时排除导航块。

每章的阅读伪代码都要给省略部分补上对应章节与职责范围，不能只写“前面已读”或裸省略号。分别标清前置准备、当前下钻、运行期间的交互和返回后的工作；可复用能力说明它覆盖哪些阶段，不强行排成独立步骤。

用 [章节 Markdown 模板](assets/chapter.md)起稿。已有章节先逐层对照：已满足的保留，缺少的补齐，冗长重复的下沉；不因模板存在就重写全章。

## 入口数据表：按实际交接建立最小理解

入口表先回答：当前有哪些东西、下一步接收哪一份、读者此刻需要怎样理解它。可以采用“此时的数据 → 下一步交给谁 → 最小理解”，列名本身不是质量标准。

- **按真实传递粒度选行。** 下一步接收整份 `body`，就先列原始请求，再解释本例从中读取 `max_tokens`；接收 `Session`，就先说明会话配置的整体职责。若实际传递的就是一个字段值，则可以直接列该值。
- **接收者与用途分开。** “下一步交给谁”写实际函数、组件或对象；“提供默认采样参数”是用途，不能代替接收者。让整张表都回答同一组问题。
- **最小理解写任务中的内容、关系或约束。** 例如“5 条按历史顺序排列的消息”保留了顺序关系；“1 个可用工具的定义”说明工具在本轮仍可使用；“提供默认采样参数和上下文预算”说明会话配置的整体作用。只写“局部变量”“对象属性”不能替代这些解释。

修改旧表时，逐行比较有没有丢掉顺序、可用性、默认值或约束等有效含义。数量、具体工具名和字段值可按本例保留，但不要让新加的类型说明挤掉原有含义。当前项目的逐行示例见 [最小理解对照](references/slime-hugo.md#入口表的最小理解对照)。

代码身份、属性归属、来源和具体成员放在附近短说明或相应步骤展开；影响当前理解的区别及时说明。这条规则针对交接总览。章节进入对象组成时，仍应按需展开成员及作用，不把对象树或其他表格硬改成这三列。

## 图、对象与例子的分工

- **局部图**讲职责和数据交接，框中使用“中文职责＋真实符号＋主要产物”。箭头区分顺序、调用、组成和数据流；并列职责不自动表示并发。
- **对象组成**确实影响理解时，在相应步骤开头加简短语义化树／列表，写成员归属、类型、具体用途和后续消费者。其余部分保留流程图即可。只列相关成员时注明范围。
- 主线通常纵向，同级组件可以并排；组件内部成员纵向，标题、步骤、符号、说明采用可辨认的字号层级。沿用项目视觉体系，不机械复制颜色或尺寸。
- **同一示例**贯穿各步，展示关键前后变化；完整输入、长 token 列表和重复的大 JSON 按需展开或下载。必要代码仍在解释旁边可读，不能只剩数据截图。
- 写清 `body["max_tokens"]` 是字典键、`state.adapter` 是属性、`prompt_ids` 是局部变量；标识要说明标识的是任务、会话还是请求。保留真实共享引用、可变性和原地修改／新建对象的区别。

## 解释与源码证据分层

正文保留代码符号、关键片段和语义解释。文件路径、行号、固定源码 URL 放在解释旁的默认收起入口；版本信息放入证据文件与固定链接，不堆到正文里。

编写或改写代码讲解时，按 [证据模板](assets/source-check.md) 另存 `SOURCE-CHECK.md`：每个 C 编号记录“核对事实 → 调用处＋定义处 → 文件／行号／固定提交 → 核对方式与结果”。记录图、示例的来源，区分静态核对、实际执行、构造响应和真实模型输出。只有材料组织审阅时，可直接在对照文件标明“未重新核对源码”，不必另造证据清单。没有执行的步骤写成待验证，不伪造结果。发现旧资料与新源码不一致时，先列差异，不悄悄更新版本标签。

对当前 Hugo/Slime 网站，接入前读 [项目映射](references/slime-hugo.md)，其中列出已采用的范例、资源与兼容入口。

## 交付检查

- 正常路径是否从入口连续走到出口？代码片段能否支持对应解释？
- 图、逐步讲解和示例是否描述同一范围？失败分支只补会改变本章行为／清理的关键项。
- 默认阅读能否不打开出处就理解？展开后能否定位调用处和实现处？
- 网页首图、折叠、源码链接、下载和下一章入口是否可用？原始材料是否按约定保留？
- 改稿提供“保留／调整／待核实”对照和可审阅候选；测试通过与读者已经掌握分开记录。

完成时给出本轮入口、修改范围、真实验证结果与尚未采用的建议。整个流程的目标是连贯解释职责，不是让所有章节长得完全相同。
